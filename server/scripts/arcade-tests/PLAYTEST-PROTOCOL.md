# คู่มือทดสอบกับผู้เริ่มต้นจริง (Arcade Battle Royale)

เอกสารนี้มีไว้เพราะเหลืออยู่ข้อเดียวที่สคริปต์ทำแทนไม่ได้ — **ต้องมีคนที่เพิ่งเริ่มเรียน Python
นั่งเล่นจริง** ตัวเลขที่วัดไปแล้ว (จำนวนตัวอักษรที่ต้องพิมพ์ เทียบกับเวลาที่มี) พิสูจน์ได้แค่ว่า
"พิมพ์ทัน" เท่านั้น ส่วน "คิดออกไหมในเวลาที่เหลือ" ไม่มีทางวัดแทนได้

---

## เกณฑ์ตัดสิน

> ผู้เริ่มต้นควรทำโจทย์สำเร็จ **อย่างน้อย 2 จาก 4 รอบ** ในห้อง **easy** โหมด **Standard (60 วินาที)**

"สำเร็จ" = ผ่าน test case ครบทุกข้อของรอบนั้น (สคริปต์รายงานนับให้เอง)

ถ้าต่ำกว่าเกณฑ์ **อย่าเพิ่งรีบแก้ตัวเลข** — ต้องรู้ก่อนว่าแพ้เพราะอะไร (ดูหัวข้อ "สามอย่างที่ต้องแยกให้ออก")

---

## เตรียมก่อนนัดคนมาเล่น

1. **สร้างบัญชีให้ผู้ทดสอบล่วงหน้า** — โหมดนี้เข้าด้วย guest ไม่ได้ (`/matchmaking` เด้งไป `/login`
   ถ้าไม่ได้ล็อกอินด้วยบัญชีจริง) ถ้าให้เขามาสมัครเองหน้างานจะเสียเวลาและเสียอารมณ์ก่อนเริ่ม
2. เปิด server (`npm start` ใน `server/`) และ client (`npm run dev` ใน `client/`) ให้เรียบร้อย
3. ตรวจว่าฐานข้อมูลทำงาน — ถ้า postgres ไม่ขึ้น การแข่งจะไม่เดินและจะดูเหมือนเกมค้าง
4. **จดชื่อผู้ใช้ของผู้ทดสอบไว้** ต้องใช้ตอนรันรายงาน
5. เตรียมกระดาษ/ไฟล์สำหรับจดตามตารางด้านล่าง

---

## สิ่งที่ควรบอกผู้ทดสอบ (และสิ่งที่ไม่ควรบอก)

**ควรบอก**
- "เป็นเกมแข่งเขียน Python แข่งกับบอท 4 ตัว มี 4 รอบ รอบละ 1 นาที"
- "โค้ดตั้งต้นมีให้แล้ว ส่วนใหญ่ต้องเติมแค่ 1-2 บรรทัดตรงที่เขียนว่า TODO"
- "ทำไม่เสร็จไม่เป็นไร เราอยากรู้ว่าเกมยากไปไหม ไม่ได้วัดว่าคุณเก่งแค่ไหน"

**ไม่ควรบอก**
- อย่าใบ้คำตอบ อย่าชี้ว่าต้องพิมพ์ตรงไหน — สิ่งที่เราอยากรู้คือเขาหาเจอเองไหม
- อย่าอธิบายว่าไอเทม hint ทำอะไร ปล่อยให้เขาค้นพบเอง (ถ้าไม่มีใครกดใช้เลย นั่นก็เป็นผลการทดสอบ)

**ขอให้เขาพูดออกมาดังๆ ว่ากำลังคิดอะไรอยู่** (think-aloud) นี่คือที่มาของข้อมูลที่ฐานข้อมูลไม่มีทางเก็บได้

---

## สามอย่างที่ต้องแยกให้ออก

รอบที่ทำไม่สำเร็จ หน้าตาในฐานข้อมูล **เหมือนกันหมด** แต่สาเหตุต่างกันสามแบบ และแก้คนละทางโดยสิ้นเชิง
นี่คืองานหลักของคนสังเกตการณ์:

| อาการที่เห็น | แปลว่า | ทางแก้ |
|---|---|---|
| อ่านโจทย์แล้วงง ถามว่า "ให้ทำอะไร" | **อ่านไม่เข้าใจ** | แก้คำอธิบายโจทย์ / ตัวอย่าง input-output |
| เข้าใจโจทย์ แต่นั่งนิ่ง ไม่รู้จะเขียนอะไร | **คิดไม่ออก** | hint, หรือลดความยากของโจทย์ในกลุ่ม easy |
| รู้ว่าต้องเขียนอะไร แต่พิมพ์ไม่ทัน/พิมพ์ผิด | **พิมพ์ไม่ทัน** | เพิ่ม scaffold, หรือลด `beginnerCharsPerMinute` ให้สุ่มโจทย์สั้นลง |
| ทำโจทย์ได้แต่ยังแพ้บอท | **บอทแข็งไป** | `botSkillByDifficulty.easy` |

---

## ขั้นตอนการทดสอบ

**แมตช์ที่ 1 — easy / Standard (60s)** ← แมตช์นี้คือแมตช์ที่ใช้ตัดสินเกณฑ์
1. ให้ผู้ทดสอบสร้างห้องเอง (ดูด้วยว่าเขาหาปุ่มเจอไหม เป็นข้อมูลอีกอย่าง)
2. ตั้งค่า: 5 คน / Standard / Easy แล้วเพิ่มบอท 4 ตัว
3. เล่นจนจบ ห้ามช่วย
4. จดตามตารางด้านล่างทุกรอบ

**แมตช์ที่ 2 — easy / Quick (30s)**
เล่นซ้ำแบบเดิมแต่โหมดเร็ว เพื่อดูว่า 30 วินาทีสนุกหรือกดดันเกินไป
(แมตช์นี้**ไม่ใช้ตัดสินเกณฑ์** เพราะเกณฑ์ตั้งไว้สำหรับ Standard)

---

## ตารางจดระหว่างเล่น

| รอบ | ชื่อโจทย์ | เสร็จไหม | ถ้าไม่เสร็จ ติดที่ไหน (อ่าน/คิด/พิมพ์) | คำพูดที่น่าสนใจ |
|---|---|---|---|---|
| 1 | | | | |
| 2 | | | | |
| 3 | | | | |
| 4 | | | | |

**คำถามหลังจบ (ถามปากเปล่า)**
1. รอบไหนสนุกที่สุด รอบไหนหงุดหงิดที่สุด
2. เห็นตัวอย่าง `fib(5) → 5` ใต้โจทย์ไหม ช่วยไหม
3. รู้ไหมว่าซื้อไอเทมช่วยใบ้โค้ดได้ ถ้าซื้อแล้วช่วยจริงไหม
4. เวลา 1 นาทีต่อรอบ รู้สึกอย่างไร แล้วโหมด 30 วินาทีล่ะ
5. อยากเล่นอีกไหม (คำถามนี้สำคัญกว่าที่คิด)

## หลังเล่นเสร็จ — ออกรายงาน

```bash
node scripts/arcade-tests/playtest-report.js <ชื่อผู้ใช้>
```

สคริปต์จะดึงแมตช์ล่าสุดของคนนั้นมาแสดงผลรายรอบ (ผ่านกี่ test case, ใช้เวลาไปเท่าไรจากที่มี,
คะแนน quality) แล้วตัดสินตามเกณฑ์ ≥2 จาก 4 ให้เลย
ถ้าจะดูแมตช์ใดเจาะจง ใส่รหัสห้องต่อท้าย เช่น `... playtest-report.js somchai ARC-XXXX`

**ข้อควรรู้**: แมตช์จะขึ้นในรายงานก็ต่อเมื่อเล่นจนถึงหน้าสรุปผล (RESULT) แล้วเท่านั้น
ถ้าปิดกลางคันจะไม่ถูกนับ

⚠️ รายงานบอกได้แค่ว่า *ทำได้หรือไม่ได้* — บอกไม่ได้ว่า *ทำไม*
เอาผลจากสคริปต์มาวางคู่กับตารางที่จดไว้เสมอ แล้วค่อยตัดสินใจว่าจะปรับอะไร

เขียน work log ที่ `project_logs/YYYY-MM-DD/HHMM-ผลทดสอบกับผู้เริ่มต้น.md` โดยแนบ:
