## สิ่งที่พบ: ปัญหาใหญ่กว่าที่คิด — พฤติกรรมบอทผูกอยู่กับ tick rate โดยตรง

ตั้งใจจะมาแค่ "ดูว่าบอทยังสมดุลอยู่ไหม" แต่พออ่านโค้ดจริงพบว่า**พฤติกรรมบอทถูกกำหนดโดยความถี่ที่ `botManager.update()` ถูกเรียก ไม่ใช่โดยค่าใน profile** ซึ่งแปลว่าการแก้บั๊ก render loop เมื่อวานได้ **rebalance เกมทั้งเกมโดยไม่ตั้งใจ**

จุดที่มีปัญหา 3 จุดใน `botAI.js`:

| จุด | กลไกเดิม | ผลกระทบ |
|---|---|---|
| ซื้อไอเทม (`maybeBuyItem`) | `Math.random() >= attackChance` **ต่อการเรียก 1 ครั้ง** ไม่มีการจับเวลา | ที่ ~164Hz บอทได้สิทธิ์สุ่มซื้อ ~3,280 ครั้งต่อช่วงร้านค้า 20 วินาที → เต็มกระเป๋าทันทีทุกตัว **ค่า `attackChance` ในแต่ละ profile แทบไม่มีความหมายเลย** |
| ใช้ไอเทมโจมตี (`maybeUseItem`) | `Math.random() >= 0.6` **ต่อการเรียก 1 ครั้ง** | ที่ ~164Hz บอทเทไอเทมทั้งกระเป๋าใส่ผู้เล่นภายในเสี้ยววินาทีที่รอบเริ่ม |
| ความคืบหน้าการเขียนโค้ด | `if (timePassed >= typingSpeedMs) { progress += 1 step }` — จับเวลาแต่เดินได้ **1 ขั้นต่อการเรียก** | ที่ tick 1 วินาที ค่า `typingSpeedMs` ถูกปัดขึ้นเป็นวินาทีถัดไป เช่น 1200ms กลายเป็น 2000ms จริง (**ช้าลง 67%**) |

### ตัวเลขผลกระทบต่อ profile (tick 1 วินาที ก่อนแก้)
```
PyNinja      typingSpeedMs=1200 -> จริง 2000ms (ช้าลง 67%)
SyntaxPro    typingSpeedMs=1300 -> จริง 2000ms (ช้าลง 54%)
CodeMaster   typingSpeedMs=1500 -> จริง 2000ms (ช้าลง 33%)
NullPointer  typingSpeedMs=1800 -> จริง 2000ms (ช้าลง 11%)
BugHunter    typingSpeedMs=2200 -> จริง 3000ms (ช้าลง 36%)
```

**หมายเหตุสำคัญ**: เรื่องนี้**ไม่กระทบผลแพ้ชนะ** เพราะคะแนนรอบของบอทถูกสังเคราะห์ฝั่งเซิร์ฟเวอร์ (`synthesizeBotRoundScore`) ไม่ได้มาจาก `progress` ฝั่ง client สิ่งที่กระทบคือ**ความรู้สึกตอนเล่น**: ความถี่การโดนแกล้ง และความเร็วหลอดความคืบหน้าของคู่แข่ง

## การแก้: เปลี่ยนทุกจุดให้อิงเวลาจริง ไม่อิงจำนวนครั้งที่ถูกเรียก

เพิ่มใน `shared/arcadeConfig.json` พร้อมคอมเมนต์อธิบายที่มา:
- `botBuyAttemptIntervalMs: 2500` — บอทตัดสินใจเรื่องซื้อได้ 1 ครั้งต่อ 2.5 วินาทีจริง
- `botItemUseIntervalMs: 4000` — บอทตัดสินใจใช้ไอเทมได้ 1 ครั้งต่อ 4 วินาทีจริง

แก้ `botAI.js`:
1. `maybeBuyItem` / `maybeUseItem` — เพิ่ม cooldown ตามเวลาจริงก่อนจะสุ่ม (เก็บ `lastBuyAttempt` / `lastItemUseAttempt`)
2. ความคืบหน้าโค้ด — เดินตามจำนวน interval ที่ผ่านไปจริง (`steps = floor(timePassed / typingSpeedMs)`) และเก็บเศษเวลาไว้ ทำให้ `typingSpeedMs` ให้จังหวะตามที่เขียนไว้จริงไม่ว่าจะ tick ถี่แค่ไหน
3. ค่าเริ่มต้นของ `lastBuyAttempt`/`lastItemUseAttempt` สุ่มเหลื่อมกันเล็กน้อย เพื่อไม่ให้บอท 5 ตัวที่ถูกเพิ่มพร้อมกันซื้อ/ยิงพร้อมกันเป๊ะทุกจังหวะ

### บั๊กที่เกือบสร้างขึ้นเอง (แก้แล้วก่อน commit)
การเปลี่ยนความคืบหน้าเป็นแบบ "เดินชดเชยตามเวลาที่ผ่านไป" ทำให้เกิดช่องโหว่: `lastActionTime` ไม่ถูกรีเซ็ตตอนขึ้นรอบใหม่ ดังนั้นเวลาที่ผ่านไปช่วง summary + ร้านค้า (~25 วินาที) จะถูกนับเป็น ~16 interval แล้ว**หลอดความคืบหน้าของบอทจะพุ่งเต็มทันทีที่รอบใหม่เริ่ม**
แก้โดยรีเซ็ต `lastActionTime` ทั้งใน `resetRoundProgress()` และ `resetState()`

## การทดสอบ

### 1. ทดสอบแบบวัดผลได้ (deterministic) — พิสูจน์ว่าไม่ผูกกับ tick rate แล้ว
เขียนสคริปต์จำลองที่ mock `Date.now()` แล้วรัน `BotAIEngine` ตัวจริงด้วย tick rate ต่างกัน บนช่วงเวลาจำลองเท่ากัน วัดว่า **ใช้เวลานานเท่าไหร่กว่าจะซื้อของเต็มกระเป๋า / ใช้ไอเทมหมดกระเป๋า** (เฉลี่ย 40 รอบต่อเคสเพื่อกลบ RNG)

**ก่อนแก้ (per-call):**
```
tick=   6ms  เติมกระเป๋าเต็มใน     15ms   ใช้ไอเทมหมดกระเป๋าใน     21ms
tick=1000ms  เติมกระเป๋าเต็มใน   2750ms   ใช้ไอเทมหมดกระเป๋าใน   3575ms
```
→ ต่างกันประมาณ **170-180 เท่า** ตาม tick rate ล้วนๆ และที่ 164Hz คือ **บอทเทไอเทมทั้งกระเป๋าใส่ผู้เล่นภายใน 21 มิลลิวินาที**

**หลังแก้ (time-paced):**
```
tick=   6ms  เติมกระเป๋าเต็มใน   8385ms   ใช้ไอเทมหมดกระเป๋าใน  17473ms
tick=1000ms  เติมกระเป๋าเต็มใน   9575ms   ใช้ไอเทมหมดกระเป๋าใน  16775ms
```
→ ต่างกันแค่ **~14% และ ~4%** ซึ่งเป็นความคลาดเคลื่อนจาก RNG ไม่ใช่จาก tick rate

**จังหวะที่ได้ตอนนี้สมเหตุสมผล**: บอทใช้เวลา ~9 วินาทีจากช่วงร้านค้า 20 วินาทีในการซื้อของจนเต็ม และกระจายการแกล้งผู้เล่น 3 ไอเทมออกไป ~17 วินาทีจากรอบ 60 วินาที

### 2. ทดสอบบนหน้าจอจริง (ห้อง `ARC-CSQF`, 5 คน: ผู้เล่นจริง + บอท 4 ตัว)
- หลอดความคืบหน้าบอทเดินต่อเนื่องเป็นธรรมชาติ ค่าเปลี่ยนทุกวินาที และวนกลับ 0 เมื่อครบ 100 — **ไม่มีอาการพุ่งเต็มทันทีตอนขึ้นรอบใหม่** (ยืนยันว่าการแก้ `lastActionTime` ได้ผล)
- ตัวอย่างค่าที่บันทึกได้ในรอบ 1: `[27,39,26,0]` → `[22,57,23,87]` → `[56,0,74,50]`
- แมตช์เดินครบผ่าน ROUND 1 → SHOP 1 → ROUND 2 → ROUND 3 ตามปกติ ไม่มี error

**ข้อจำกัดของการทดสอบบนหน้าจอ**: ไม่สามารถนับความถี่การโดนแกล้งได้อย่างน่าเชื่อถือ เพราะ Chrome throttle แท็บที่อยู่เบื้องหลัง ทำให้ตัวเก็บตัวอย่างในหน้าเว็บพลาดการแจ้งเตือนที่แสดงอยู่แค่ 4 วินาที — จึงใช้การทดสอบแบบ deterministic ข้อ 1 เป็นหลักฐานหลักแทน ซึ่งวัดตรรกะตัวจริงโดยไม่ขึ้นกับเบราว์เซอร์
