## 1. ปัญหาที่แก้

โจทย์เขียนโค้ดกระจายอยู่ 4 ตาราง ตารางละคนสร้าง ทั้งสี่เก็บของเดียวกัน (หัวข้อ คำอธิบาย
โค้ดตั้งต้น เฉลย test case) แต่สะกดคนละแบบ:

| ตาราง | แถว | รูปแบบ test case |
|---|---|---|
| `exercises` | 120 | `[{input, expected}]` |
| `mini_game_exercises` | 19 | object `{expected_format, rules[], correctness[]}` (บางแถวเป็น array เปล่า) |
| `multiplayer_challenges` | 13 | `[{input, output}]` — **คีย์ต่างจากที่อื่น และไม่ตรงกันเองด้วย** |
| `arcade_tasks` | 40 | `[{input:[args], output}]` — เรียกฟังก์ชัน |

ผล: มีตัวตรวจคำตอบ 5 ตัวเขียนแยกกัน และโจทย์ที่เขียนให้โหมดหนึ่งเอาไปใช้อีกโหมดไม่ได้

## 2. โครงสร้างที่เลือก

```
problems       ตัวโจทย์ (สองภาษา, starter/solution, test_kind, test_cases ที่ normalize แล้ว)
problem_modes  ทะเบียนว่าโหมดไหนใช้ข้อนั้น + ค่าเฉพาะโหมด   PK (mode, entry_id)
```

**many-to-many โดยตั้งใจ** ตามที่ผู้ใช้ระบุ — โจทย์ข้อเดียวลงทะเบียนได้ทุกโหมด
โจทย์ที่อยู่โหมดเดียวก็แค่มีทะเบียนใบเดียว

ตารางเดิมทั้งสี่กลายเป็น **view** อ่านได้เหมือนเดิมทุกจุด (~41 จุดไม่ต้องแก้เลย)
แต่เขียนไม่ได้ — จุดเขียนทั้ง 4 ย้ายไปใช้ `createProblem(mode, {...})` ตัวเดียว
ตั้งใจให้ view ไม่ updatable เพื่อให้โค้ดที่เผลอเขียนผ่านชื่อเก่า **error ทันทีแทนที่จะเงียบ**

### เรื่องที่ตอนวางแผนยังไม่รู้ และเปลี่ยนวิธีทำ

พบว่ามี **FK 12 เส้นชี้เข้ามาที่ 3 ใน 4 ตาราง** หลายเส้นมี `ON DELETE CASCADE` ที่พฤติกรรมจริง
พึ่งอยู่ (ลบมินิเกมต้องพาบทสนทนาไปด้วย) และ view เป็นเป้าของ FK ไม่ได้
ผู้ใช้เลือกให้ทำตารางจริงพร้อมย้าย FK

ทางออกที่ทำให้ **ไม่ต้องเปลี่ยนเลข id เดิมสักตัว**: `problem_modes` ใช้ PK แบบ composite
`(mode, entry_id)` โดย `entry_id` คือ id เดิมของโหมดนั้น แล้วให้ตารางลูกเพิ่ม
**generated column ค่าคงที่** บอกโหมดของตัวเอง FK จึงกลายเป็น composite ชี้ไป `(mode, entry_id)` ได้

เหตุผลที่ id ห้ามเปลี่ยน มีสองข้อ ไม่ใช่ข้อเดียว:
- FK 12 เส้น
- **`arcade_rooms.round_task_ids`** เก็บ id โจทย์ Arcade ไว้ใน jsonb ของทุกห้องที่เคยเล่น
  ถ้าเปลี่ยนเลข ประวัติแมตช์ที่จบไปแล้วจะชี้ผิดข้อแบบเงียบๆ

ทดสอบ generated column + composite FK + CASCADE บน PG 18 ใน transaction ทิ้งก่อน แล้วค่อยเขียนจริง

## 3. บั๊กที่เจอระหว่างทาง

**มินิเกม 12 จาก 19 ด่านใช้งานไม่ได้อยู่** — `test_cases_json` ของ id 8–19 เก็บ JSON ที่ถูก
escape ซ้อน (`\\"` แทน `"`) จึง parse ไม่ผ่านเลย `MiNi_Game.jsx` อ่านไม่ออกทั้ง 12 ด่าน

ไล่ต้นตอแล้ว: ในไฟล์ dump ของ Person 2 **ทั้ง 19 แถวเป็นแบบนี้หมด** คือฐานของเขาพังมาก่อนแล้ว
การนำเข้าเมื่อวานยกมาตรงตามต้นทาง ส่วน id 1–7 ของเราได้สำเนาที่สะอาดจาก Person 1 จึงไม่พัง
ซ่อมแล้วครบ 19/19 parse ผ่าน

**เพิ่มเข้ามาเองแล้วจับได้** — รอบแรกเก็บ `expires_at` เป็นข้อความ ISO ใน jsonb แล้ว cast กลับเป็น
`timestamp without time zone` ทำให้กำหนดหมดอายุของโจทย์แข่งทุกข้อ**เลื่อนไป 7 ชั่วโมง**
แก้เป็นคอลัมน์ timestamp จริง แล้วดึงค่าถูกกลับมาจากตาราง `_pre_merge` ที่ยังเก็บไว้

**PostgreSQL ไม่ยอมให้ FK ที่มี generated column ใช้ `ON DELETE SET NULL`** —
เจอตอนรันจริง (`virtual_emails.related_exercise_id`) ทางเลือกที่เหลือผิดทั้งคู่: CASCADE จะลบเมลของ
ผู้เล่นเพราะโจทย์ถูกลบ ส่วน NO ACTION จะบล็อกการลบโจทย์ คอลัมน์นี้เป็น nullable และตอนนี้ไม่ชี้
ไปที่ไหนเลย จึงปล่อยไม่ผูก FK พร้อมบันทึกเหตุผลไว้ในโค้ด

**transaction ทำงานจริง** — ครั้งที่ล้มด้วยเรื่อง SET NULL ข้างบน ตรวจแล้วตารางทั้งสี่ยังเป็น
table เดิมครบ ไม่มี `problems` ค้าง ไม่มีเศษครึ่งๆ
