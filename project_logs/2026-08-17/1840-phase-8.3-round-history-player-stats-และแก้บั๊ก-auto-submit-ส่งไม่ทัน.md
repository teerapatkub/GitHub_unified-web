## 1. Phase 8.3 — Round History & Player Stats

### ตารางใหม่ใน `server/db.js` (2 ตาราง)

**`arcade_round_history`** — บันทึกว่าผู้เล่นจริงส่งอะไรไว้ในแต่ละรอบ
- คอลัมน์: `room_id`, `user_name`, `round_num`, `code`, `pass_count`, `total_count`, `quality_score`, `time_used_seconds`, `round_score`
- `UNIQUE (room_id, user_name, round_num)` กันแถวซ้ำต่อรอบ
- `ON DELETE CASCADE` ตาม `arcade_rooms` — เป็นข้อมูลระดับแมตช์สำหรับหน้า RESULT เท่านั้น จึงล้างตัวเองไปพร้อมห้อง (เหมือน `arcade_participants`/`arcade_effects`) **ข้อจำกัดที่ต้องรู้: เมื่อผู้เล่นออกจากห้องแล้วห้องถูกลบ ประวัติรอบก็หายไปด้วย** — ยืนยันแล้วจากการทดสอบ (หลังเก็บกวาดห้องทดสอบทั้งหมด `arcade_round_history` เหลือ 0 แถว) ถ้าภายหลังต้องการให้ย้อนดูโค้ดเก่าข้ามแมตช์ได้ ต้องเปลี่ยนดีไซน์ตรงนี้
- บอทไม่เคยเขียนลงตารางนี้ (ไม่มีโค้ดให้ย้อนดู และคะแนนบอทสังเคราะห์ฝั่งเซิร์ฟเวอร์)

**`arcade_player_stats`** — สถิติสะสมข้ามแมตช์ของผู้เล่นจริง
- คอลัมน์: `user_name` (PK), `matches_played`, `wins`, `best_rank`, `total_score`, `total_cash_earned`, `updated_at`
- **ตั้งใจไม่ผูก FK กับ `arcade_rooms`** เพราะห้องถูกลบทันทีที่ว่าง แต่สถิติต้องอยู่ต่อ — ยืนยันแล้วว่ารอดจากการลบห้องจริง
- คีย์ด้วย `user_name` เพราะเป็น identity ที่ระบบ arcade ใช้อยู่แล้ว (`arcade_participants` ไม่มีคอลัมน์ `user_id`)

### จุดที่เขียนข้อมูล (server)
- **ประวัติรอบ**: ใน `POST /rooms/:id/submit-round` ใช้ `ON CONFLICT DO NOTHING` และครอบ `try/catch` แยก — **ห้ามให้ปัญหาการเขียนประวัติทำให้การส่งคำตอบล้มเหลว** คะแนนของผู้เล่นสำคัญกว่าแถวประวัติ
- **สถิติสะสม**: ฟังก์ชันใหม่ `recordArcadePlayerStats(roomId)` เรียกจาก `finalizeArcadePhase()` ตรงจุดที่เปลี่ยน phase เป็น `RESULT` — ตรวจแล้วว่า**มีที่เดียวในระบบทั้งหมดที่ตั้ง `RESULT`** และ `tickArcadeMatches()` ข้ามห้องที่อยู่ใน `RESULT` อยู่แล้ว จึงนับซ้ำไม่ได้
- อันดับคิดเทียบกับทุกคนในห้องรวมบอท (ได้ที่ 2 ในห้อง 5 คนก็คือที่ 2 ไม่ว่าคู่แข่งจะเป็นบอทกี่ตัว) และอ่านจาก `score` สะสมตัวเดียวกับที่หน้า RESULT ใช้จัดอันดับ เพื่อให้ "ชนะ" ตรงกับผู้ชนะที่ผู้เล่นเห็นจริงเสมอ

### Endpoint ใหม่ (2 ตัว)
- `GET /rooms/:id/round-history?user_name=` — **จำกัดเฉพาะของตัวเอง** โดยเจตนา ถ้าคืนโค้ดของทุกคนตอนจบแมตช์ หน้า RESULT จะกลายเป็นเฉลยคำตอบ
- `GET /players/:user_name/stats` — คืนค่าศูนย์ทั้งหมดแทน 404 สำหรับคนที่ยังไม่เคยจบแมตช์ ให้ client วาดการ์ดได้เลยไม่ต้องเช็ค

### ฝั่ง client
- `hooks/useProgression.js` (ใหม่) — hook อ่านอย่างเดียว ไม่เคยเขียนอะไร จึงไม่มีทางกระทบผลการแข่งขัน รับ **primitive** (`playerName`, `roomId`) ไม่ใช่ object `currentRoom` เพื่อไม่ให้ effect re-subscribe ทุกครั้งที่ poller ทำงาน (บทเรียนจากบั๊ก render loop เมื่อเช้านี้)
- `widgets/RoundHistoryPanel.jsx` (ใหม่) — แสดงบนหน้า RESULT กดแต่ละรอบเพื่อกางโค้ดที่ส่งไป พร้อมที่มาของคะแนน 3 ส่วน (เทสต์/คุณภาพ/เวลา) ให้คะแนนที่ได้อธิบายได้ ไม่ใช่เลขลอยๆ
- `widgets/PlayerStatsCard.jsx` (ใหม่) — การ์ดสถิติเหนือรายการห้องในล็อบบี้ 6 ช่อง (แมตช์/ชนะ/อัตราชนะ/อันดับดีสุด/คะแนนรวม/เงินที่หาได้) มีการ์ดกันหารศูนย์ตอนยังไม่เคยเล่น
- `translations.js` — เพิ่ม 12 คีย์ใหม่ TH/EN

## 2. บั๊กที่เจอระหว่างทดสอบ: ระบบส่งคำตอบอัตโนมัติ "ส่งไม่ทัน" เสมอ

### อาการ
เล่นแมตช์จริงผ่านเบราว์เซอร์แล้ว**ตั้งใจไม่กดปุ่มส่งคำตอบ**ในรอบ 2 ผลคือไม่มีแถวประวัติของรอบ 2 เลย และคะแนนรอบ 2 เป็น 0

### สาเหตุราก
`submitMyRound()` ต้องทำงาน async หลายวินาทีก่อนจะยิง POST ได้:
1. รันโค้ดผู้เล่นผ่าน Pyodide (~1 วินาทีขึ้นไป)
2. เรียก AI judge ประเมินคุณภาพโค้ด (~1-5 วินาที)
3. **แล้วจึง** POST `/submit-round`

แต่ safety net เดิมยิงตอน `remaining === 0` พอดี — กว่า POST จะออกไป เซิร์ฟเวอร์ปิดรอบไปแล้ว (`tickArcadeMatches` ทำงานทุก 1 วินาที) endpoint จึงตอบ 400 `ไม่อยู่ในช่วงเวลาที่ส่งคำตอบได้` **แปลว่า safety net นี้แทบไม่มีทางสำเร็จเลย** ใครไม่กดปุ่มเองก็ได้ 0 ทุกครั้งแบบเงียบๆ

หมายเหตุ: ก่อนแก้บั๊ก render loop เมื่อเช้านี้ `timeLeft` ไม่เคยถึง 0 เลย safety net จึงไม่เคยยิงด้วยซ้ำ — บั๊กสองตัวนี้ซ้อนกันอยู่ พอแก้ตัวแรกแล้วตัวที่สองจึงโผล่ให้เห็น

### การแก้
เพิ่ม `autoSubmitLeadSeconds: 8` ใน `shared/arcadeConfig.json` (พร้อมคอมเมนต์อธิบายว่าทำไม**ห้ามเป็น 0**) แล้วเปลี่ยนเงื่อนไขจาก `remaining === 0` เป็น `remaining <= AUTO_SUBMIT_LEAD_SECONDS` เพื่อให้ POST ลงถึงเซิร์ฟเวอร์ก่อนรอบปิด
ยิงซ้ำได้ทุกวินาทีในช่วง lead โดยไม่มีผลเสีย เพราะ `submitMyRound()` ตั้ง `hasSubmittedThisRound` ทันทีตอนเริ่ม และมี `submittingRoundRef` กันซ้ำอีกชั้น

### ผลข้างเคียงที่ต้องยอมรับ
ผู้เล่นที่ยังพิมพ์อยู่ตอนเหลือ 8 วินาทีจะถูกส่งโค้ดที่พิมพ์ไว้ ณ จุดนั้นและถูกล็อกไม่ให้แก้ต่อ — แลกกับการไม่ได้ 0 คะแนน ถือว่าดีกว่าของเดิมชัดเจน แต่ถ้าอยากให้เนียนกว่านี้ ควรมีข้อความเตือนบนหน้าจอตอนเข้าช่วง 8 วินาทีสุดท้าย (ยังไม่ได้ทำ)

### ทดสอบบนหน้าจอจริง (เบราว์เซอร์ Chrome จริง)
- **การ์ดสถิติในล็อบบี้**: PASS — ตอนยังไม่มีแมตช์แสดงเลขศูนย์ทั้งหมด + ป้าย "ยังไม่มีแมตช์ที่จบ"; หลังจบแมตช์จริงแสดง 1 แมตช์ / 0 ชนะ / 0% / #2 / 250 คะแนน / 🪙 900 **ตรงกับแถวใน DB ทุกช่อง**
- **แผงย้อนดูโค้ดบนหน้า RESULT**: PASS — แสดง "รอบ 1 | ✅ 4/4 | 📖 90/100 | ⏱ 24s | 250 pt" พร้อมปุ่มกางดูโค้ด
- **ความถูกต้องของคะแนนที่บันทึก**: PASS — ส่งโค้ด Fibonacci จริงได้ 4/4 เทสต์, คุณภาพ 90, ใช้เวลา 24 วินาที → `round_score` 250 ตรงกับสูตร 100 + 90 + ((60−24)/60×100 = 60) เป๊ะ
- **ยังไม่ได้ยืนยันบนหน้าจอ**: การยิง auto-submit ที่วินาทีที่ 8 จริงๆ — แท็บทดสอบถูก Chrome throttle/freeze ทำให้ interval ไม่ทำงานในช่วง lead window (ข้อจำกัดเครื่องมือทดสอบ ไม่ใช่บั๊กแอป) พิสูจน์ได้แค่ระดับ API ว่า "ส่งก่อน 8 วินาทีรับ / ส่งหลังปิดปฏิเสธ" ซึ่งเป็นสมมติฐานที่การแก้อาศัยอยู่
