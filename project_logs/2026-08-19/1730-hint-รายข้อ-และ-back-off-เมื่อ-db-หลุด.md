# hint รายข้อ 40 ชุด + back-off เมื่อฐานข้อมูลหลุด

**วันที่**: 2026-08-19 เวลา 17:30
**ผู้ทำ**: Person 3 (Arcade Battle Royale)

งานสองอย่างที่ค้างไว้จากรอบก่อน ทำเสร็จทั้งคู่ — และระหว่างทางเจอต้นตอของบั๊ก log ที่ค้างมานาน

## งานที่ 1 — hint รายข้อ (แทนข้อความคงที่ข้อความเดียว)

### ปัญหาเดิม

ไอเทม `aiHelper` ราคา 600 เรียก `setPlayerState(prev => ({ ...prev, hint: t('aiHint') }))`
คือแสดง **ข้อความเดียวกันทุกโจทย์ทั้ง 40 ข้อ**: "ลองใช้วิธีวนซ้ำ หรือใช้ดิกชันนารีเพื่อลดเวลาประมวลผล"
ซึ่งไม่เกี่ยวกับโจทย์ตรงหน้าเลย จึงไม่มีเหตุผลที่ใครจะซื้อ

### สิ่งที่ทำ

เพิ่ม `hint_th` / `hint_en` ให้ทุกข้อใน `server/arcadeTaskSeed.js` (40 × 2 = 80 ข้อความ)
พร้อมคอลัมน์ `hint_th`, `hint_en` ใน `arcade_tasks` (เพิ่มล้วน ไม่มี DROP/TRUNCATE)

**หลักการเขียน hint**: scaffold มี TODO บอก *ว่าต้องทำอะไร* อยู่แล้ว หน้าที่ของ hint คือส่วนที่ TODO ไม่ได้บอก —
**ใช้เครื่องมืออะไรของ Python ทำ ทำไมต้องอันนั้น และกับดักที่ทำให้ครั้งแรกพัง** แต่ไม่ใช่บรรทัดคำตอบ
ตัวอย่าง (Binary Search):

> ลบ break ออกแล้วขยับขอบเขตแทน ถ้าค่ากลางน้อยเกินไปคำตอบอยู่ครึ่งขวา ให้ low ขยับไปถัดจาก mid
> ถ้ามากเกินไปคำตอบอยู่ครึ่งซ้าย ให้ high ถอยมาก่อน mid — **ต้องขยับให้พ้น mid ไม่งั้นช่วงไม่เคยแคบลงและลูปวนไม่จบ**

**ทางเดินของข้อมูล**: hint ติดไปกับ `shapeTask()` ซึ่งเป็นจุดเดียวที่แปลงแถวใน DB เป็น "รอบนี้คือโจทย์อะไร"
เหมือนกับ title / desc / starter code — ตั้งใจไม่ให้ไปดึงแยก เพราะการดึงแยกคือสาเหตุที่ทำให้รอบ 4
เคยแสดงหัวข้อกับโค้ดคนละโจทย์กันเมื่อเช้านี้

ฝั่ง `useCombat` รับ `activeRoundHintRef` เข้าไป (ต้องใช้ ref เพราะ `useCombat()` ถูกสร้างก่อนจุดที่
resolve โจทย์ของรอบ และเพราะ hint ที่เปลี่ยนไม่ควรทำให้ handler ทั้งชุดถูกสร้างใหม่)
ถ้าไม่มี hint ในแถวนั้นจะ fallback เป็นข้อความเดิม ไอเทมจึงทำอะไรบางอย่างเสมอ

### กฎใหม่ในสคริปต์ตรวจ

`verify_tasks.py` เพิ่มการตรวจ hint 2 ข้อ (รวมเป็น **458 assertions** จากเดิม 378):
มีครบทั้งสองภาษา และ **ต้องไม่มีบรรทัดคำตอบอยู่ในข้อความ hint แบบตรงตัว**

กฎข้อหลังจับได้จริง **6 ข้อ** ที่เขียนหลุดไปให้คำตอบตรงๆ (`total += n`, `count += 1`,
`freq[char] = freq.get(char, 0) + 1`, `high = mid - 1`, `out.extend(sub)`, `return not stack`)
ทั้งหมดถูกเขียนใหม่ให้อธิบายเครื่องมือแทนการยกบรรทัดคำตอบมาแปะ

## งานที่ 2 — back-off เมื่อฐานข้อมูลหลุด

### ปัญหาเดิม

`setInterval(tickArcadeMatches, 1000)` ยิงทุกวินาทีไม่ว่าครั้งก่อนจะสำเร็จหรือไม่
ตอน postgres restart ใต้เซิร์ฟเวอร์เมื่อ 2026-08-18 จึงพ่น error 56,492 บรรทัดก่อนตาย

### สิ่งที่ทำ

เปลี่ยนทั้ง tick และ stale-room sweep จาก `setInterval` เป็น `setTimeout` ที่ตั้งเวลาตัวเองใหม่ ด้วยเหตุผล 2 ข้อ:

1. **Back-off** — ล้มเหลวติดกันแล้วหน่วงเพิ่มเป็นเท่าตัวจนถึงเพดาน 30 วินาที และกลับสู่ 1 วินาทีทันทีที่สำเร็จ
   การหน่วงไม่ทำให้เสียอะไร เพราะระหว่างที่ต่อ DB ไม่ได้ก็เลื่อน phase ไม่ได้อยู่แล้ว
   และเพราะ `phase_deadline` เก็บเป็น timestamp ไม่ใช่ตัวนับถอยหลังในหน่วยความจำ
   พอกลับมาได้ tick ที่สำเร็จครั้งเดียวก็เก็บห้องที่ครบกำหนดระหว่างนั้นได้หมด
2. **Tick ไม่ซ้อนกัน** — `setInterval` ไม่รอ callback ที่เป็น async ถ้า tick หนึ่งทำงานนาน
   (ห้องเยอะ หรือ query ช้า) tick ถัดไปจะเริ่มทับ แล้ว **ทั้งคู่จะอ่านห้องเดียวกันจาก SELECT เดิม
   แล้ว finalize ซ้ำ จ่ายคะแนนและเงินสองรอบ** การตั้งเวลาใหม่หลังงานเสร็จเท่านั้นตัดปัญหานี้ทิ้งโดยโครงสร้าง

log ยังถูกจำกัดด้วย: บันทึกครั้งแรกเต็มๆ จากนั้นเฉพาะครั้งที่เป็นเลขยกกำลังสอง (1, 2, 4, 8, ...)
พร้อมบรรทัดแจ้งตอนกลับมาทำงานได้

## 🔍 ต้นตอของบั๊ก log ที่ค้างมานาน — เจอแล้ว

ระหว่างทำงานนี้ เซิร์ฟเวอร์ **ตายด้วย exit code 4 ต่อหน้า** ซึ่งเป็นอาการเดียวกับที่รายงานไว้
log เดิมมี 2,500 บรรทัด และ 2,336 บรรทัดคือ:

```
❌ Arcade match tick error:
```

**ไม่มีอะไรอยู่หลัง colon เลย** — นั่นคือเหตุผลที่บั๊กนี้ไม่เคยถูกวินิจฉัย

สาเหตุที่ข้อความว่าง: โค้ดเดิมพิมพ์ `err.message` เฉยๆ และตัว error ที่เกิดจริงคือ
**`AggregateError` ซึ่ง `.message` เป็นสตริงว่าง** — Node สร้างมันขึ้นเมื่อ `net.createConnection`
ต่อไม่สำเร็จ ข้อมูลที่มีประโยชน์อยู่ใน `.code` (`ECONNREFUSED`) ซึ่งไม่เคยถูกพิมพ์ออกมา

แก้โดยเพิ่ม `describeError()` ที่พิมพ์ name / code / message / sql / เฟรมแรกของ stack
และเมื่อ message ว่างจะ dump ตัว object ออกมาแทน ตอนนี้ log อ่านได้จริง:

```
❌ Arcade match tick failed (attempt 2, retrying in 4000ms): AggregateError [ECONNREFUSED] <no message> {"code":"ECONNREFUSED"}
```

พร้อมกันนั้นทำให้ทุกทางที่ throw ออกจาก `server/db.js` มีข้อความบอกว่าพังตรงไหน
(`PG_SOCKET_ERROR`, `PG_CONNECTION_CLOSED`, `PG_TIMEOUT`)

## ⚠️ สิ่งที่ยัง "ไม่รู้" และไม่ได้แก้ — ระบุตรงๆ

1. **สาเหตุที่ tick พังทั้งที่ postgres ยังทำงานปกติ ยังหาไม่เจอ**
   log เดิมแสดง error ตั้งแต่วินาทีแรกหลังบูต โดยที่ฐานข้อมูลใช้งานได้ปกติตลอด (ล้มราว 43% ของ tick)
   ทดลองแยกออกมารัน query เดียวกัน 80 ครั้ง (ทั้งแบบเรียงและแบบพร้อมกัน 6 เส้น) — **ผ่านหมด ไม่ล้มเลย**
2. **การแก้ socket lifecycle ใน db.js พิสูจน์ไม่ได้ว่าแก้ปัญหาข้อ 1**
   ทำการทดลองแบบมีกลุ่มควบคุม: ถอดการแก้ออก แล้วรัน load ชุดเดียวกัน (23 ห้อง) —
   **ได้ 0 error เท่ากันทั้งสองแบบ** จึงสรุปไม่ได้ว่าการแก้นั้นคือสิ่งที่ทำให้ log สะอาด
   เก็บไว้เพราะเป็นการทำให้ lifecycle ชัดเจนขึ้น แต่ **ไม่นับเป็นการแก้บั๊ก**
3. **สมมติฐาน IPv6/IPv4 — ทดสอบแล้วว่าผิด** เดาไว้ว่า `localhost` อาจ resolve เป็น `::1` แล้วถูกปฏิเสธ
   ตรวจจริง: `localhost` ให้ทั้ง `::1` และ `127.0.0.1` และ **ต่อได้ทั้งคู่** (docker bind ทั้งสอง stack)
   จึงไม่ใช่สาเหตุ
4. **exit code 4 เกิดจากอะไร ยังไม่ทราบ** — ไม่มี stack trace ตอนตาย

**สิ่งที่เปลี่ยนไปจริงคือ**: ถ้าอาการนี้กลับมาอีก log จะบอกได้แล้วว่าเป็น error อะไร code อะไร
และจะมีไม่กี่สิบบรรทัดแทนหลายหมื่นบรรทัด — คือทำให้ *วินิจฉัยได้* ไม่ใช่ *แก้หายแล้ว*

## การทดสอบที่ทำจริง

### hint

| การทดสอบ | ผล |
|---|---|
| `verify_tasks.py` | 40 ข้อ / **458 assertions** ผ่านหมด (รวมกฎ hint 2 ข้อ) |
| กฎ "hint ห้ามมีบรรทัดคำตอบ" | **จับได้จริง 6 ข้อ** แล้วเขียนใหม่จนผ่าน |
| DB + API | 40/40 แถวมี `hint_th` และ `hint_en` ครบ, `GET /api/arcade/tasks` ส่งออกมาถูกต้อง |
| **บนหน้าจอจริง (ห้อง ARC-T29D)** | ซื้อ `AI บอกใบ้โค้ด` จากร้านค้าจริงแล้วกดใช้ในรอบ 3 (โจทย์ "12. ผลรวม 1 ถึง n") → ขึ้นข้อความ **"💡 range(1, n + 1) ให้ 1 ถึง n — ต้อง +1 เพราะ range ไม่รวมตัวสุดท้าย แล้วบวกเข้า total ในลูป"** ซึ่งเป็น hint ของโจทย์ข้อนั้นพอดี ไม่ใช่ข้อความกลางแบบเดิม |

### back-off

ทดสอบด้วยการ **หยุด postgres จริง** (`docker stop postgres`) แล้วเปิดกลับ 2 รอบ:

| สิ่งที่วัด | ผล |
|---|---|
| การหน่วงเพิ่มขึ้น | 2000ms → 4000ms → 16000ms → 30000ms (ชนเพดาน) ตามที่ออกแบบ |
| log ระหว่าง outage | บันทึกเฉพาะครั้งที่ 1, 2, 4, 8 ตามที่ตั้งใจ |
| **จำนวน log ทั้งหมดของ outage ~2 นาที** | **19 บรรทัด** (เทียบกับ 56,492 บรรทัดของเดิม) |
| การกลับมาทำงาน | อัตโนมัติทั้งสองลูป: `✅ Arcade match tick recovered after 7 failed attempt(s)` และ `✅ Arcade stale-room sweep recovered after 4 failed attempt(s)` |
| ข้อความ error | อ่านรู้เรื่องแล้ว: `AggregateError [ECONNREFUSED]` แทนบรรทัดว่าง |

## สิ่งที่ยังไม่เสร็จ

1. **สาเหตุที่แท้จริงของ tick error ตอน DB ปกติ** — ยังไม่ทราบ (ดูหัวข้อ ⚠️ ด้านบน)
   ครั้งหน้าที่เกิด ให้ดู log ที่ตอนนี้จะบอก code ของ error แล้ว
2. **hint ภาษาอังกฤษยังไม่ได้ทดสอบบนหน้าจอ** — ยืนยันแค่ระดับ API ว่าข้อมูลถูกส่งออกมาครบ
   (โค้ดเลือกภาษาเป็นบรรทัดเดียวกับที่ใช้กับ title/desc ที่ทดสอบบนหน้าจอไปแล้ว)
3. **ยังไม่มีคนจริงลองอ่าน hint** ว่าช่วยให้คิดออกจริงไหม — วัดแทนด้วยสคริปต์ไม่ได้
