## 2. สิ่งที่แก้ไข

### 2.1 เพิ่ม `starter_code` ให้โจทย์ทั้ง 40 ข้อ — `server/arcadeTaskSeed.js`, `server/db.js`

เดิม editor ให้ผู้เล่นเริ่มจากบรรทัด `def name(args):` + `# Write your python code here` + `pass`
คือต้องพิมพ์โครงสร้างทั้งหมดเองทุกข้อ ตอนนี้ทุกข้อมี **scaffold** ที่ให้ตัวแปรตั้งต้น ลูป และ `return` มาแล้ว
เว้นเฉพาะ 1-2 บรรทัดที่เป็นแก่นของโจทย์ พร้อมคอมเมนต์ภาษาไทยบอกว่าต้องทำอะไร ตัวอย่าง:

```python
def count_vowels(s):
    vowels = "aeiou"
    count = 0
    for char in s:
        # TODO: ถ้า char.lower() อยู่ใน vowels ให้ count เพิ่มขึ้น 1
        pass
    return count
```

**การเปลี่ยนความหมายของ `initial_code`** — เดิมเก็บเฉลยแบบสั้นที่สุด (เช่น
`return sum(1 for char in s if char.lower() in "aeiou")`) ตอนนี้เก็บ **เฉลยที่ scaffold พาไปถึง**
(เวอร์ชันลูปตามตัวอย่างข้างบน) เหตุผล: ถ้าเฉลยอ้างอิงกับเฉลยที่ scaffold พาไปถึงเป็นโค้ดคนละแบบ
ค่า `work_chars` (ข้อ 2.2) จะไปวัดเฉลยที่ไม่มีใครถูกชี้นำให้เขียน และเวอร์ชันลูปยังเหมาะกับ
แอปที่สอนผู้เริ่มต้นมากกว่าเฉลยบรรทัดเดียวอยู่แล้ว `initial_code` ยังไม่เคยถูกส่งให้ผู้เล่นเห็นเหมือนเดิม

**Schema**: เพิ่มคอลัมน์ `starter_code TEXT` และ `work_chars INTEGER` ใน `arcade_tasks`
ผ่าน `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` ใน `server/db.js` — **เพิ่มล้วน ไม่มี DROP/TRUNCATE**
และ seed upsert (match `title_en`) เขียนค่าลงทั้งสองคอลัมน์ให้แถวเดิมทั้ง 40 แถว
`GET /api/arcade/tasks` ใช้ `SELECT *` จึงส่งฟิลด์ใหม่ถึง client เองโดยไม่ต้องแก้

**ฝั่ง client**: `shapeTask()` ใน `useRoundJudging.js` ใช้ `source.starter_code` ถ้ามี
(fallback เป็นพฤติกรรมเดิมถ้าเป็นแถวรุ่นเก่าที่ยังไม่มีค่า) และ `getRound4Task()`
เปลี่ยนไปเรียก `shapeTask()` แทนการทำ regex ซ้ำอีกชุด — สองฟังก์ชันนี้เคยเป็นสำเนากันและ
**เคย drift จริง** (รอบ 4 เสิร์ฟ fallback ที่ hardcode ไว้อยู่นานโดยไม่มีใครเห็น เพราะ fallback
บังเอิญเหมือนโจทย์แรกของ pool เป๊ะทุกไบต์)

### 2.2 สุ่มโจทย์ให้พอดีกับเวลาของรอบ — `drawArcadeRoundTasks()` ใน `server/server.js`

เพิ่ม `work_chars` = จำนวนตัวอักษรของเฉลยที่ **ยังไม่ได้อยู่บนหน้าจอใน scaffold**
คือปริมาณที่ผู้เล่นต้องพิมพ์จริง คำนวณด้วยสคริปต์ตอน generate seed ไม่ใช่เขียนมือ
(นับบรรทัดของเฉลยที่ไม่ปรากฏเป็นบรรทัดใน scaffold โดยไม่นับคอมเมนต์กับ `pass`)

การสุ่มกรองด้วยงบเวลาก่อน:
```
budget = (roundSeconds - autoSubmitLeadSeconds) * beginnerCharsPerMinute / 60
```
`roundSeconds` อ่านจาก `arcadePhaseDurations(room)` ที่มีอยู่แล้ว → ห้องโหมดเร็วได้งบสั้นกว่าอัตโนมัติ
(โหมดเร็ว 33 ตัวอักษร, มาตรฐาน 78 ตัวอักษร)

มี fallback สำคัญ: ถ้ากรองแล้วเหลือน้อยกว่าที่ต้องใช้ (โหมดสั้นมาก หรือแถวรุ่นเก่าที่ `work_chars`
ยังเป็น NULL) จะเรียงจากสั้นสุดมาใช้แทน **ห้ามคืน `null`** เพราะจะทำให้แมตช์ถอยไปใช้โจทย์
built-in ตายตัวอย่างเงียบๆ

### 2.3 รอบ 4 ปรับระดับตามห้อง — `shared/arcadeConfig.json` + 3 จุดที่ตัดสินใจเรื่องรอบ 4

เดิมรอบ 4 ดึงจาก `hard` เสมอไม่ว่าห้องจะเลือกระดับอะไร ห้อง easy จึงมีรอบตัดสินที่ไม่มีใครในห้องทำได้
กลายเป็นรอบที่ทุกคนได้ 0 เท่ากันและไม่ได้ตัดสินอะไรเลย

เพิ่ม `finalePoolByDifficulty` = `easy → medium`, `default → medium`, `medium → hard`, `hard → hard`
รอบชิงยังยากกว่ารอบ 1-3 เสมอ แค่ไต่ตามระดับห้องแทนที่จะกระโดดสุดทาง
แก้ให้ตรงกันทั้ง 3 จุด: การสุ่ม, fallback หาจำนวน test case ของห้องรุ่นเก่าใน server,
และ fallback ของ `getRound4Task()` ฝั่ง client — ถ้าไม่ตรงกัน บอทจะถูกให้คะแนนเทียบโจทย์คนละข้อกับที่คนเห็น

### 2.4 โชว์ตัวอย่าง input/output — `BattleRoyaleGameplayView.jsx`

เดิมหน้าโจทย์แสดงแค่ชื่อกับคำอธิบายเป็นตัวอักษรล้วน ผู้เริ่มต้นต้องเดาว่าค่าที่ต้อง return
หน้าตาเป็นอย่างไร (ลิสต์หรือจำนวน, `True` หรือสตริง `"True"`) ทั้งที่ `test_cases` ส่งมาถึงหน้าจอแล้ว

ตอนนี้แสดงตัวอย่าง `count_vowels("hello") → 2` ใต้คำอธิบาย โดยแสดงแค่ `exampleCasesShown` (= 2)
จาก 4-5 เคส เพื่อไม่ให้เอาไปทำเป็นตาราง lookup ที่ผ่านเคสที่ซ่อนไว้ได้
มีฟังก์ชัน `pyLiteral()` เรนเดอร์ค่าแบบ Python (`True`/`False`/`None`) ไม่ใช่แบบ JS
เพราะการโชว์ `true` ใต้โจทย์ Python คือการบอกให้ผู้เล่นพิมพ์สิ่งที่ไม่มีในภาษา

### 2.5 คะแนนเวลาต้องแลกมาด้วยความถูกต้อง — client + server พร้อมกัน

เดิม `timeScore = ((roundDuration - timeUsed) / roundDuration) * 100` **แยกจากความถูกต้องสิ้นเชิง**
แปลว่าคนที่กดส่งโค้ดเปล่าทันทีที่รอบเปิดได้คะแนนเวลาเกือบ 100 ส่วนคนที่สู้จนผ่าน 3/5 ตอนใกล้หมดเวลา
ได้แค่ ~17 → **กติกาให้รางวัลกับการยอมแพ้มากกว่าการตั้งใจทำ** และกลุ่มที่โดนกระทบหนักสุดคือผู้เริ่มต้น
เพราะเป็นกลุ่มที่มีแนวโน้มจะไม่มีอะไรจะส่งมากที่สุด

เปลี่ยนเป็น `timeScore = passRatio * ((roundDuration - timeUsed) / roundDuration) * 100`
แก้ **ทั้งสองฝั่งพร้อมกัน** (`useRoundJudging.js` และ `synthesizeBotRoundScore()`) —
ถ้าแก้แค่ฝั่งคน บอทจะยังได้คะแนนเวลาฟรีต่อไปกลายเป็นเอาเปรียบคนแทน

### 2.6 ความเก่งของบอทตามระดับห้อง — `synthesizeBotRoundScore()`

เดิมบอทใช้ช่วงสุ่มคงที่ (`0.35 + rand*0.65` สำหรับสัดส่วนเทสที่ผ่าน, `40 + rand*50` สำหรับ quality)
ไม่ว่าห้องจะตั้งระดับอะไร เลือกห้อง easy จึงได้โจทย์ง่ายลงแต่เจอคู่แข่งแข็งเท่าเดิม = ไม่ได้ง่ายขึ้นจริง

เพิ่ม `botSkillByDifficulty` ใน `arcadeConfig.json` โดยตั้งค่า **`medium` ให้เท่ากับพฤติกรรมเดิมเป๊ะ**
เพื่อให้ตรวจสอบย้อนกลับได้ว่าอะไรเปลี่ยนเพราะอะไร

### 2.7 บั๊กที่เจอตอนทดสอบบนหน้าจอจริง (ไม่ได้อยู่ในแผนเดิม)

ห้อง ARC-VB44: หน้าโจทย์ขึ้น **"Sum Array"** พร้อมตัวอย่าง `sum_array([1,2,3,4]) → 10` ถูกต้อง
แต่ editor กลับโหลด **`def fib(n):` + `pass`** ของโจทย์ built-in คนละข้อ

สาเหตุ: room poller รับ payload ใหม่ → เรียก `setCurrentRoom()` → แล้ว **ตัดสินใจเรื่องการเปลี่ยน phase
ใน tick เดียวกัน** ตอนนั้น React ยังไม่ re-render `currentRoom` จึงยังเป็นห้องเดิมที่ยังไม่มี
`round_task_ids` → `getPoolTask(1)` คืน `null` → fallback ไปใช้โจทย์ตายตัว
(`taskResolverRef` แก้เรื่อง resolver ค้างเก่าไปแล้ว แต่ตัว state ที่ resolver อ่านยังค้างอยู่ใน tick นั้น)

แก้โดยให้ `getPoolTask(roundNum, roomOverride)` และ `getRound4Task(roomOverride)`
รับ payload สดเข้ามาได้ แล้วให้ทุกจุดที่ถือ payload อยู่แล้วส่งเข้าไปตรงๆ แทนการอ่านย้อนจาก state
รวมถึง resume path ใน `useRoomLifecycle.js` ที่มีข้อบกพร่องเดียวกัน (กลับเข้าแมตช์กลางรอบแล้วได้
โจทย์ built-in แทนโจทย์ที่แมตช์สุ่มมา) — จุดนี้เดิมยังไม่รองรับรอบ 1-3 จาก pool เลย

### 4.3 ข้อจำกัดของการทดสอบ (ระบุตรงๆ)

- **ยังไม่มีคนจริงพิมพ์เอง** — การทดสอบ "เขียนคำตอบทันเวลา" ทำโดย set ค่าใน editor ผ่านสคริปต์
  ไม่ใช่พิมพ์ทีละตัวอักษร สิ่งที่พิสูจน์แล้วคือ **scaffold ที่เติมเสร็จถูกตรวจถูกต้องครบทาง end-to-end**
  ส่วน "พิมพ์ทันไหม" พิสูจน์ด้วยการนับตัวอักษรใน `difficulty_analysis.py` และ
  "คิดออกไหมในเวลานั้น" ยัง **ต้องให้คนจริงลองเล่นเท่านั้น** — วัดแทนไม่ได้
- ระหว่างทดสอบพบว่า **สคริปต์ทดสอบของตัวเองผิด**: set ค่าใน editor แล้วกด submit ใน tool call เดียวกัน
  ทำให้ React ยังไม่ได้อัปเดต `playerState.code` → ระบบตรวจ scaffold เปล่าแทนคำตอบ (ได้ 2/5 พร้อม quality 15
  ซึ่งเป็นคะแนนของ scaffold เอง) แก้โดยแยกเป็นสอง call แล้วได้ 5/5 ทันที — เป็นบั๊กของสคริปต์ ไม่ใช่ของแอป
- ยังไม่ได้ทดสอบห้อง `medium` และ `default` บนหน้าจอ (ทดสอบผ่าน API แล้วใน `draw_test.js`)

## 5. ผลกระทบต่อส่วนอื่นของระบบ

- **Bot AI Engine: ไม่กระทบเรื่องเนื้อโจทย์** — ตรวจแล้วว่า `botAI.js` จำลองความคืบหน้าเป็นตัวเลข %
  ล้วน ไม่เคยอ่านเนื้อโจทย์ อ่านแค่ *จำนวน* test case ผ่านฝั่ง server การเพิ่ม `starter_code`/`work_chars`
  จึงไม่แตะ bot เลย **แต่** ข้อ 2.5 และ 2.6 เปลี่ยนคะแนนบอทโดยตรง (คะแนนเวลาต้องแลกด้วยความถูกต้อง
  + ความเก่งตามระดับห้อง) — ห้อง `medium` เท่าเดิมเป๊ะ, `hard` เก่งขึ้น, `easy`/`default` อ่อนลง
- **Schema**: เพิ่มคอลัมน์ล้วน ไม่มี DROP/TRUNCATE ไม่มีการแก้ฐานข้อมูลด้วยมือ ทุกอย่างผ่าน `server/db.js`
  แถวเดิมทั้ง 40 แถวยังคง `task_id` เดิม (upsert match `title_en`) ประวัติแมตช์เก่าไม่กระทบ
- **Query ทั้งหมดยังเป็น parameterized `?` placeholder** รวมถึง query ใหม่ใน `drawArcadeRoundTasks()`
  (`WHERE difficulty = ?` และ `IN (...)` ที่สร้าง placeholder จากความยาว array ไม่ใช่ต่อสตริงค่า)
- **ห้องรุ่นเก่า**: แถวที่ `work_chars` เป็น NULL ถือว่า `Infinity` → ตกไปอยู่กลุ่ม fallback ไม่ทำให้การสุ่มพัง
  และ `shapeTask()` ยัง fallback เป็นพฤติกรรมเดิมถ้าไม่มี `starter_code`
- **ระดับความยากที่ผู้เล่นรู้สึก** เปลี่ยนไปมากในทางที่ง่ายขึ้น — ถ้าจะปรับกลับ จุดเดียวที่ต้องแก้คือ
  `beginnerCharsPerMinute` (งบเวลา) และ `botSkillByDifficulty` ใน `shared/arcadeConfig.json`

## 6. สิ่งที่ยังไม่ทำ / ควรทำต่อ

1. **hint รายข้อ** — ตอนนี้ไอเทม `aiHelper` ราคา 600 แสดงข้อความคงที่ `t('aiHint')` ข้อความเดียว
   ทุกโจทย์ ซึ่งแทบไม่มีประโยชน์ ควรเพิ่ม `hint_th`/`hint_en` รายข้อแล้วให้ไอเทมโชว์ hint ของโจทย์จริง
   (ต้องเขียนเนื้อหาเพิ่ม 40 ชุด จึงกันไว้เป็นงานรอบถัดไป ตกลงกับผู้ใช้ไว้แล้วว่าไม่รวมรอบนี้)
2. **ให้คนจริงลองเล่น** — เป็นข้อเดียวที่วัดแทนด้วยสคริปต์ไม่ได้ ต้องดูว่าเวลาที่เหลือหลังหักเวลาพิมพ์
   พอให้ "คิดออก" หรือไม่ โดยเฉพาะโหมดเร็ว 30 วินาที
3. **server ไม่มี back-off เมื่อ DB หลุด** (ปัญหาเดิมที่ยังไม่แก้) — เคยพบว่า postgres restart แล้ว
   server พ่น error 56,492 ครั้งติดกันก่อนตาย (exit code 4)
4. ทดสอบห้อง `medium`/`default` บนหน้าจอจริง (ผ่าน API แล้ว)
