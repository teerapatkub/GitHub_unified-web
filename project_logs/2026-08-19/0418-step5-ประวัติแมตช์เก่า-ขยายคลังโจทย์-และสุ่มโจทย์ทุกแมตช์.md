## ส่วนที่ 1 — Step 5: ประวัติรอบต้องอยู่รอดหลังห้องถูกลบ

### ปัญหา
`arcade_round_history` ผูกกับ `arcade_rooms` ด้วย `ON DELETE CASCADE` แต่ห้องถูกลบทันทีที่ว่าง แปลว่า **ผู้เล่นเสียโค้ดของตัวเองทันทีที่ออกจากห้อง** ย้อนดูแมตช์เก่าไม่ได้เลย

### การแก้
- **ตัด FK ทิ้ง** (`DROP CONSTRAINT IF EXISTS`) แล้วเก็บ `room_code` / `room_name` ไว้ในแถวประวัติเอง เพื่อให้ยังบอกได้ว่าเป็นแมตช์ไหนแม้ห้องหายไปแล้ว
- เพิ่ม `match_ended_at` ประทับตอนแมตช์จบจริง (ในจุดเดียวกับที่บันทึกสถิติ ซึ่งทำงานครั้งเดียวต่อแมตช์) ใช้เป็นตัวบอกด้วยว่า "แมตช์นี้จบสมบูรณ์" — แมตช์ที่เล่นค้างไว้จะไม่โผล่ในรายการ
- **เพิ่ม retention แทน cascade**: เมื่อไม่มี cascade มาคุมขนาดตารางแล้ว ต้องมีขอบเขตของตัวเอง → `roundHistoryKeepMatchesPerPlayer: 10` เก็บ 10 แมตช์ล่าสุด**ต่อผู้เล่น** (ไม่ใช่เพดานรวมหรือช่วงเวลา เพื่อไม่ให้คนที่เล่นนานๆ ครั้งเสียประวัติเพราะคนอื่นเล่นเยอะ) กวาดทุก 1 ชั่วโมง
- Endpoint ใหม่ `GET /players/:user_name/history` — จำกัดเฉพาะของตัวเองเหมือนเดิม (ถ้าคืนของทุกคนก็กลายเป็นเฉลย)
- UI: `PastMatchesPanel` ในล็อบบี้ กดขยายแต่ละแมตช์แล้วใช้ `RoundHistoryPanel` ตัวเดิมแสดงผล เพื่อให้แมตช์เก่าอ่านเหมือนแมตช์ที่เพิ่งจบ

### ผลทดสอบ

|---|---|
| แมตช์ที่ยังไม่จบไม่โผล่ในประวัติ | PASS |
| แมตช์ที่จบแล้วโผล่พร้อมชื่อ/รหัสห้อง | PASS |
| ประวัติเก็บโค้ดที่ส่งไว้ครบ | PASS |
| **ห้องถูกลบจริง (API ตอบ 404) แต่ประวัติยังเรียกดูได้** | **PASS** — ยืนยันด้วย SQL ว่า `room_exists = f` และ endpoint ยังคืนข้อมูลพร้อมโค้ด |

## ส่วนที่ 2 — ขยายคลังโจทย์

### สิ่งที่ทำ
- **เพิ่ม test case ให้โจทย์เดิมทุกข้อ ข้อละ 3 เคส** — เดิมหลายข้อมีแค่ 1 เคส ทำให้คะแนนส่วนความถูกต้องเป็นได้แค่ 0 หรือ 100 ตอนนี้ทุกข้อมี 4-5 เคส (รวม 189 เคส) คะแนนจึงละเอียดขึ้นจริง
- **เพิ่มโจทย์ใหม่ประเภทละ 5 ข้อ** → ง่าย 15, กลาง 15, ยาก 10 (รวม 40 ข้อ จากเดิม 25)
- ย้ายคลังโจทย์ออกมาเป็นไฟล์ `server/arcadeTaskSeed.js` และเปลี่ยนจาก "seed เฉพาะตอนตารางว่าง" เป็น **upsert ทุกครั้งที่บูต** (จับคู่ด้วย `title_en`) — เดิมถ้าตารางมีข้อมูลแล้วจะแก้อะไรไม่ได้เลยโดยไม่ล้างตาราง

### 🐛 บั๊กข้อมูลที่พบและแก้ (สำคัญ)
โจทย์ **"6. Longest Word"** มีเฉลยอ้างอิงเป็น `max(words, key=len)` ซึ่ง Python คืน**คำแรก**ที่ยาวที่สุด → `"The quick brown fox jumps"` ได้ `"quick"`
แต่ test case ที่เก็บไว้คาดหวัง `"jumps"`
**แปลว่าผู้เล่นที่ทำถูกจะถูกตัดสินว่าผิด** และเฉลยอ้างอิงของระบบเองก็สอบตกข้อสอบตัวเอง — แก้ค่าที่คาดหวังเป็น `"quick"` แล้ว

### วิธีป้องกันไม่ให้เกิดซ้ำ
เขียนสคริปต์ตรวจ (`verify_tasks.py`) ที่**รันเฉลยอ้างอิงของทุกโจทย์กับทุก test case ใน Python จริง**
- ผลลัพธ์: **40 โจทย์ / 189 test case ผ่านหมด**
- ทดสอบตัวตรวจเองด้วยการจงใจใส่ค่าผิด 2 จุด (รวมถึงย้อนบั๊ก longest_word กลับ) → ตัวตรวจจับได้ทั้งคู่ ยืนยันว่าไม่ใช่การผ่านแบบหลอกๆ

## ส่วนที่ 3 — สุ่มโจทย์ทุกแมตช์ (ไม่ล็อกว่ารอบไหนเป็นข้อไหน)

### หลักการออกแบบที่สำคัญที่สุด
**สุ่มครั้งเดียวตอนเริ่มแมตช์ แล้วบันทึกไว้ที่ห้อง** (`arcade_rooms.round_task_ids`)
เหตุผล: เซิร์ฟเวอร์ใช้จำนวน test case ของโจทย์เพื่อปรับสเกลคะแนนบอท ส่วน client ใช้โจทย์เดียวกันตรวจผู้เล่น **ถ้าต่างฝ่ายต่างสุ่มเอง บอทจะถูกให้คะแนนเทียบกับโจทย์ที่ไม่มีใครได้ทำ** — เป็นกับดักเดียวกับที่เคยเจอใน Phase 8.4

### กติกาการสุ่ม
- รอบ 1-3 สุ่มจากระดับความยากที่ห้องเลือก (ถ้าเป็น `default` สุ่มจาก easy+medium)
- รอบ 4 สุ่มจากคลัง `hard` เสมอ เพื่อให้รอบชิงยังเป็นรอบชิง
- สุ่มแบบไม่ซ้ำ (Fisher-Yates + กรองไม่ให้รอบ 4 ซ้ำกับรอบ 1-3 กรณีห้องระดับ hard ที่ใช้คลังเดียวกัน)
