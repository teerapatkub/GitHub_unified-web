## 1. ความสำเร็จ — เขียนเงื่อนไขใหม่ทั้ง 20 และทำระบบปลดล็อก

**ปัญหาเดิม**: ทั้ง 20 รายการเขียนไว้สำหรับโหมด simulation ที่ลบไปแล้ว
(จ่ายค่าใช้จ่าย ซื้อกาแฟ เอาชีวิตรอด 30 วัน จบเกมด้วยเงิน 10 ล้าน) — ไม่มีทางได้แม้แต่อันเดียว
และไม่มีโค้ดที่ไหนเขียนลง `user_achievements` เลย ตารางว่างทั้งฐาน

**วิธีที่เลือก**: ให้แต่ละความสำเร็จบอก **`metric` + `threshold`** ไว้ในตาราง
แล้วเขียนตัวประเมินตัวเดียวที่คำนวณ metric ของผู้เล่นแล้วปลดล็อกสิ่งที่ถึงเกณฑ์
— เพิ่มความสำเร็จใหม่ทีหลังคือเพิ่มแถวใน `db.js` ไม่ใช่เขียน if เพิ่มอีกอัน

### 20 รายการใหม่ อิงโหมดที่มีจริง

**เกณฑ์ "เรียนจบบท"** ใช้นิยามเดียวกับหน้าโปรไฟล์: ผ่านแบบทดสอบหลังเรียนที่ 60%
และทำแบบฝึกหัดของบทนั้นครบ — ไม่ได้ตั้งเกณฑ์ใหม่ซ้อนขึ้นมาอีกชุด

### ตัวประเมิน
เรียกหลังทุกเหตุการณ์ที่ทำให้ตัวเลขขยับ: ส่งแบบทดสอบ, ส่งแบบฝึกหัด, จบมินิเกม,
จบแมตช์ Arcade, ซื้อของในร้าน (ทั้งชิ้นเดียวและยกเซ็ต)

สิ่งที่ตั้งใจ:
- **ห้าม throw** — ความสำเร็จคือของแถม การให้รางวัลพลาดต้องไม่ทำให้การส่งงานหรือแมตช์ที่ได้มานั้นพัง
- **กันแจกซ้ำที่ตัว INSERT เอง** (`INSERT ... WHERE NOT EXISTS`) ไม่ใช่แค่ SELECT ก่อน
  เพราะสองเหตุการณ์ที่จบพร้อมกันอาจผ่าน SELECT ทั้งคู่
- **จ่ายรางวัลผ่าน `applyXpRewardToUser`** ตัวเดียวกับที่ทุกโหมดใช้ ทองจึงเข้ากระเป๋าเดียวกัน
- ตอบกลับ `new_achievements` ไปกับ response ของเหตุการณ์นั้น ให้ client เอาไปแจ้งเตือนได้

### ผู้ใช้เลือกเองว่าจะโชว์อันไหน
ใช้ตาราง `user_profile_showcase` ที่ติดมากับข้อมูลของ Person 1 อยู่แล้ว (มี unique key พร้อม)
- `PUT /api/profile/:userId/showcase` — บันทึกรายการที่เลือก (สูงสุด 6)
- หน้าโปรไฟล์แสดงเฉพาะที่เลือก + ปุ่ม "เลือกที่จะโชว์" + รายการทั้งหมดยุบไว้ใน `<details>`

ข้อกำหนดที่ใส่ไว้:
- **เลือกได้เฉพาะอันที่ปลดล็อกแล้ว** ไม่งั้นโปรไฟล์จะโฆษณาสิ่งที่ไม่เคยทำได้
- **ยังไม่เคยเลือก → แสดงอันที่ปลดล็อกล่าสุดแทน** โปรไฟล์จะได้ไม่ว่างเปล่าเพียงเพราะไม่มีใครไปตั้งค่า
- ตัดตัวซ้ำก่อนนับจำนวน (ส่ง id ซ้ำมาไม่ควรโดนปฏิเสธทั้งที่จริงเลือกไม่เกิน)

## 2. แบบสำรวจตอนสมัครบัญชีใหม่

**ที่พบตอนสำรวจ**: มีแบบสำรวจอยู่แล้วและทำงานตอนสมัครจริง แต่**สมัครไม่จบ**

คำถามสุดท้ายคือคำถามที่ตัดสินเลเวลเริ่มต้น โค้ดฝั่ง client เช็คด้วย `currentQ.id === 3`
แต่แถวที่ถือคำถามนั้นจริงๆ มี **id 1003** (เป็นฉบับซ้ำที่ encoding พัง)
เงื่อนไขจึงไม่เคยเข้า → กดตอบข้อสุดท้ายแล้วไม่มีอะไรเกิดขึ้น **ผู้ใช้ใหม่ค้างอยู่ตรงนั้น**
และคำถามอีก 3 ข้อที่เห็นก็เป็นตัวอักษร `?` ล้วน

ยิ่งกว่านั้น **คำตอบถูกทิ้งทั้งหมด** — `user_survey_responses` ไม่มีโค้ดที่ไหนเขียนลงเลย

### ที่ทำ
ออกแบบใหม่ 4 คำถาม เรียงโดยตั้งใจ (คำถามความชอบก่อน คำถามประสบการณ์ไว้ท้ายสุด
เพราะตอบข้อนั้นแล้วจะพาไปแบบวัดระดับและจบแบบสำรวจ):

1. **goal** — อยากเรียน Python ไปทำอะไร (5 ตัวเลือก)
2. **style** — เรียนรู้ได้ดีที่สุดด้วยวิธีใด (3)
3. **time** — ตั้งใจใช้เวลาสัปดาห์ละเท่าไร (3)
4. **experience** — เคยเขียนโปรแกรมมาก่อนไหม (3) → "ยังไม่เคยเลย" เริ่มเลเวล 1,
   อีกสองอันเข้าแบบวัดระดับ

การแก้เชิงโครงสร้าง:
- เพิ่ม `question_key` — client เลิกพึ่ง id ที่ hardcode ไว้
- ย้ายตัวเลือกที่มีเลเวลมาไว้ใน `survey_options.level_value` แทนที่จะ UNION ตาราง `level_config` เข้ามา
- `/api/survey` ส่งเฉพาะคำถามที่ `is_active = 1` — ฉบับที่พังยังอยู่ในตารางแต่ปิดไว้ ไม่ได้ลบ
- **`POST /api/survey/responses`** เก็บคำตอบจริง ตอบซ้ำจะแทนที่ของเดิม ไม่ทับถมเป็นหลายแถว
- ฝั่ง client เพิ่มแถบความคืบหน้า "คำถามที่ N จาก 4" และไฮไลต์ตัวเลือกที่เลือกไว้แล้ว
  (ย้อนกลับมาดูได้ว่าตอบอะไรไป)
- guest ตอบได้แต่ไม่บันทึก (ไม่มีแถวให้ผูก) — ไม่ใช่ error

### เทสต์ของตัวเองที่เปราะ แล้วแก้
ชุดทดสอบร้านค้าตกไป 1 ข้อในรอบแรกหลังเพิ่มระบบความสำเร็จ — ไม่ใช่บั๊กของระบบ
