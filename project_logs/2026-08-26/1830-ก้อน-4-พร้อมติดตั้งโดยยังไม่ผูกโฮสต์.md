## สรุปสั้น

ก่อนหน้านี้เว็บนี้ **ติดตั้งที่อื่นไม่ได้เลย** ไม่ใช่เพราะโค้ดผิด แต่เพราะที่อยู่ของ API
ถูกเขียนตายเป็น `localhost` ไว้ 52 จุด ไม่มีไฟล์ประกอบ container ไม่มีใครเสิร์ฟหน้าเว็บที่ build แล้ว
และ **ไม่มีอะไรในโค้ดที่สร้างตารางหลักของระบบเลย**

ตอนนี้ `docker compose up --build` แล้วได้ระบบที่ใช้งานได้จริงทั้งระบบบนเครื่องเปล่า

## 1. ที่อยู่ของ API มาจากการตั้งค่า (story 30)

`http://localhost:3001` ถูกเขียนไว้ตรงๆ **52 จุดใน 21 ไฟล์** ซึ่งเป็นเหตุผลข้อเดียวที่ทำให้
deploy ไม่ได้ — ผู้ใช้จริงทุกคนจะยิง request ไปที่เครื่องของตัวเอง

รวมเหลือที่เดียวคือ `client/src/config/api.js` ค่าเริ่มต้นเป็น **สตริงว่าง = ที่อยู่เดียวกับหน้าเว็บ**
ซึ่งถูกต้องทั้งสองสภาพแวดล้อม: ตอน deploy จริง API เป็นคนเสิร์ฟหน้าเว็บเอง
ส่วนตอนพัฒนา Vite proxy `/api` และ `/uploads` ไปให้ โค้ดจึงมีรูปแบบเดียว ไม่ใช่สองแบบ

`VITE_API_BASE_URL` มีไว้เผื่อกรณีแยก API ไปอีกโฮสต์จริงๆ เท่านั้น

**เพิ่ม `/uploads` เข้า proxy ของ Vite ด้วย** — พอ URL กลายเป็น relative รูปโปรไฟล์
สื่อของบทเรียน และงานศิลป์ของเครื่องแต่งตัวจะโหลดไม่ขึ้นทันทีถ้าไม่ทำ

**ฝั่ง server** ก็มีที่เขียนตายอยู่ 3 จุด: URL ที่ตอบกลับตอนอัปโหลด (เก็บลงฐานข้อมูลแล้วถูกอ่าน
อีกหลายเดือนต่อมา → เปลี่ยนเป็น relative), ลิงก์ยืนยันอีเมล (**ต้อง**เป็น absolute เพราะเปิดจาก
โปรแกรมเมลอีกวัน → `PUBLIC_BASE_URL`), และ asset ของเครื่องแต่งตัวใน `db.js`
ที่ seed เป็น absolute ไว้ 4 รายการ พร้อม migration เขียนแถวเดิมให้เป็น relative
(ครอบคลุม `localhost:5000` ที่หลงมาจากโปรเจครุ่นก่อนด้วย)

## 2. เสิร์ฟหน้าเว็บจาก process เดียวกับ API (story 32)

`server.js` เสิร์ฟ `client/dist` เองพร้อม SPA fallback ทำให้ทั้งระบบเป็น
**process เดียว origin เดียว port เดียว** ผลพลอยได้คือ **ไม่มีคำขอข้ามโดเมนเหลืออยู่เลย**
จึงไม่มี CORS ให้ตั้งผิดบนโดเมนที่ยังไม่ได้ซื้อ

ข้ามไปเงียบๆ ถ้าไม่มี `dist/` ซึ่งคือสภาพตอนพัฒนา

`PORT` อ่านจาก environment แล้ว (โฮสต์ส่วนใหญ่กำหนดพอร์ตมาให้)

## 3. ไฟล์ประกอบ container (story 31)

`Dockerfile` สองสเตจ — build หน้าเว็บแล้วเอาแต่ผลลัพธ์ไปต่อ + runtime ที่มี Node **และ Python
พร้อมไลบรารีที่โจทย์ใช้** ซึ่งเป็นเหตุผลที่ไฟล์นี้ไม่ใช่ของเสริม: ระบบตัดสินคำตอบด้วยการรัน
Python จริง โฮสต์ Node ธรรมดาจึงตรวจคำตอบไม่ได้เลย

`server/requirements.txt` — flask, pandas, requests, matplotlib, pytest
**ได้จากการอ่าน `solution_code` ของโจทย์ทุกข้อในฐานข้อมูล ไม่ได้เดา**
(tkinter จงใจไม่ใส่ 5 ข้อที่ import มันต้องมีจอ รันในเซิร์ฟเวอร์ไม่ได้อยู่ดี)

รายละเอียดที่ตั้งใจ: ติดตั้งลง virtualenv ไม่ใช่ Python ของ Debian · ตั้ง `MPLBACKEND=Agg`
เพราะถ้า matplotlib พยายามเปิดหน้าต่าง คำตอบของผู้เรียนจะค้างจนโดน timeout แล้วถูกตัดสินว่าผิด ·
ทำ symlink `python` เพราะตัวรันเรียกชื่อนี้แต่ Debian ติดตั้งมาแค่ `python3`

## 4. ⭐ เว็บนี้ไม่เคยติดตั้งใหม่ได้เลย — เพิ่งรู้ตอนลองจริง

**นี่คือสิ่งที่สำคัญที่สุดในก้อนนี้ และหาไม่เจอด้วยการอ่านโค้ด**

พอ container พร้อมแล้วลองรันกับฐานข้อมูลเปล่า ปรากฏว่า API บูตสวยงามแล้วตอบทุก request ว่า

```
relation "users" does not exist
```

`db.js` สร้างเฉพาะตารางที่ตัวเองดูแล (arcade_*, problems, ร้านค้า, ความสำเร็จ, แบบสำรวจ)
ส่วน `users`, `lessons`, `lesson_slides`, `quiz_questions` และที่เหลือ **ไม่เคยมีโค้ดตรงไหนสร้างเลย**
มันอยู่บนเครื่องพัฒนามาตลอดเพราะเคย restore จากไฟล์ dump เมื่อนานมาแล้ว
เนื้อหาบทเรียนทั้งหมดก็เหมือนกัน

**แก้:** `server/scripts/dump-schema.js` สร้างสองไฟล์จากฐานข้อมูลที่ใช้งานอยู่จริง

| ไฟล์ | มีอะไร |
|---|---|
| `server/schema.sql` (147 KB) | 63 ตาราง + 4 view + ดัชนี + constraint + trigger **ไม่มีข้อมูลสักแถว** |
| `server/seed-content.sql` (666 KB) | บทเรียน 24 · สไลด์ 220 · คำถาม 190 · คลังโจทย์ 192 · ร้านค้า · ความสำเร็จ |

`db.js` เอาไปใช้ตอนบูต **เฉพาะเมื่อไม่มีตาราง `users`** ระบบที่ติดตั้งไปแล้วไม่ถูกแตะเลย

**เรื่องข้อมูลส่วนบุคคล** — รายชื่อตารางที่ถูกดัมป์เป็น **whitelist ที่เขียนไว้ชัด** ไม่ใช่รายการยกเว้น
เพราะรายการยกเว้นตั้งต้นด้วยการ "เอาทุกอย่าง" และตารางแรกที่ลืมยกเว้นแปลว่าบัญชีจริง
อีเมลจริง และรหัสผ่านที่ hash ไว้หลุดเข้า git ตรวจซ้ำแล้ว: ไม่มีแถวของ `users`
ไม่มี pattern ของ bcrypt และไม่มีตารางที่ขึ้นต้นด้วย `user_` เลย

### สี่อย่างที่พังระหว่างทาง และเจอได้เพราะรันจริงเท่านั้น

| อาการ | สาเหตุ |
|---|---|
| `schema "public" already exists` | pg_dump เขียน `CREATE SCHEMA public` มาด้วย ซึ่งทุกฐานข้อมูลมีอยู่แล้ว statement แรกล้มแล้วพาทั้งไฟล์ล้มตาม |
| `schema "fullprojectpython" does not exist` | trigger 10 ตัวใน public เรียกฟังก์ชันที่อยู่อีก schema (ของเลียนแบบ `ON UPDATE CURRENT_TIMESTAMP` จากสมัยยังเป็น MySQL) ต้องดัมป์มาด้วย |
| `syntax error at or near "2"` | pg_dump ใช้ `COPY ... FROM stdin` ซึ่งเป็น protocol ที่ node-postgres ไม่รู้จัก เปลี่ยนเป็น `--column-inserts` |
| `no schema has been selected to create in` | pg_dump ล้าง `search_path` ของ session ทิ้ง ซึ่งถูกต้องสำหรับ psql ที่ทิ้ง connection หลังใช้ แต่ที่นี่มันคืน connection กลับเข้า pool พร้อม path ที่ว่างเปล่า query ถัดไปที่หยิบ connection นั้นเลยพัง |

**และอีกอย่างที่เจอเพราะฐานข้อมูลเปล่า** — `db.js` กับ `ensureMergedSchemas()` ใน `server.js`
เคยทำงาน **พร้อมกัน** ซึ่งมองไม่เห็นเลยบนฐานข้อมูลที่มีตารางครบ (ทั้งคู่ไม่ทำอะไร)
แต่บนฐานข้อมูลเปล่ามันแย่งกันสร้างตารางเดียวกัน ฝ่ายที่แพ้ได้ `already exists`
แล้วทิ้งงานที่เหลือของตัวเองไปทั้งหมด แก้ด้วย `db.ready` ที่ `server.js` รอก่อน

## 5. ไฟล์อัปโหลดไม่หายตอนอัปเดต (story 33)

`UPLOADS_DIR` ตั้งค่าได้ compose ผูก volume ไว้ที่ `/data/uploads` **นอกโฟลเดอร์แอป**
เพราะนี่คือสถานะเดียวของระบบที่ไม่ได้อยู่ในฐานข้อมูล การ deploy ทับของเดิมจะลบรูปโปรไฟล์
ของทุกคนไปพร้อมกัน

## ยังไม่ได้ทำ

- **ยังไม่ได้เลือกโฮสต์จริง** ตามสเปกที่ตั้งใจให้เป็นการตัดสินใจแยก
- ยังไม่ได้ตั้ง HTTPS / reverse proxy — ขึ้นกับโฮสต์ที่จะเลือก
- `PUBLIC_BASE_URL` ต้องตั้งจริงตอนมีโดเมน ไม่งั้นลิงก์ยืนยันอีเมลจะยังชี้ localhost
- ยังไม่มีการสำรองฐานข้อมูลอัตโนมัติ
