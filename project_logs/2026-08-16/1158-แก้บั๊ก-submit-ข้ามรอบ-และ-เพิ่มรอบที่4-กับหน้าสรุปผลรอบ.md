## สิ่งที่แก้ไข

### 1) บั๊กจริง: กดส่งคำตอบแล้วข้าม phase ทันที
**สาเหตุ**: `handleManualSubmit()` เรียก `handlePhaseTransition()` ตรงๆ หลังบันทึกว่าส่งแล้ว ทำให้ข้ามเวลาที่เหลือไปเลยไม่ว่า timer จะเหลือเท่าไหร่
**แก้ไข**: ลบการเรียก `handlePhaseTransition()` ออกจาก `handleManualSubmit()` เหลือแค่ตั้ง `hasSubmittedThisRound: true` (ผู้เล่นกลายเป็นผู้ชมรอดูคนอื่น ปุ่มไอเทมถูกปิดตามเงื่อนไขเดิมที่มีอยู่แล้ว) การเปลี่ยน phase จริงๆ เกิดจาก timer effect เพียงจุดเดียวเมื่อเวลาหมดจริงเท่านั้น — นี่คือจุดที่ทำให้ผู้ใช้เข้าใจผิดว่า "ตัวจับเวลาค้าง" เพราะไม่เคยเห็นมันนับถอยหลังเลยตอนกดส่งคำตอบ

### 2) เพิ่มหน้าสรุปอันดับ + เหรียญที่ได้รับ (Round Summary) ก่อนเข้าร้านค้า
**ตกลงกับผู้ใช้**: กำหนดเวลาคงที่ 5 วินาทีแล้วตัดเข้าร้านค้าอัตโนมัติ (ไม่ใช้ปุ่มกดเอง เพราะเสี่ยงปัญหา sync ถ้าผู้เล่นบางคนไม่กด)
**แก้ไข**:
- เพิ่ม phase ใหม่ 3 ตัว: `SUMMARY_1`, `SUMMARY_2`, `SUMMARY_3` (ใช้ระบบ timer/deadline เดียวกับที่มีอยู่แล้ว รวมอยู่ใน `startPhaseTimer(5)`)
- เพิ่ม state `roundSummary` เก็บ `{roundNum, entries: [{name, isPlayer, rank, cashGain, eliminated}]}` — สร้างขึ้นภายใน `evaluateRound()` แล้ว return กลับมาให้ `handlePhaseTransition()` เซ็ตก่อนเปลี่ยนไป phase SUMMARY
- สร้างไฟล์ใหม่ `client/src/pages/widget/RoundSummaryView.jsx` แสดงหมายเลขรอบ, นับถอยหลังก่อนเข้าร้านค้า, ตารางอันดับพร้อมเหรียญที่ได้และป้าย "ตกรอบ" ถ้ามี
- **จุดที่ต้องระวังเป็นพิเศษ**: อันดับที่ใช้แจกเหรียญ (คำนวณจากคะแนน**เฉพาะรอบนั้น**) กับอันดับที่ใช้ตัดสินว่าใครตกรอบ (คำนวณจากคะแนน**สะสม**ทั้งหมด ตรงกับ logic เดิมของ `eliminateBottom`) เป็นคนละการจัดอันดับกัน — ถ้าใช้อันดับเดียวกันผิดจุดจะทำให้ป้าย "ตกรอบ" ในหน้าสรุปแสดงผิดคนจากที่ `eliminateBottom()` ตัดจริง จึงคำนวณแยกกัน 2 ชุดใน `evaluateRound()` แล้วรวมผลด้วยชื่อผู้เล่น

### 3) เพิ่มรอบเล่นเป็น 4 รอบ, ย้ายจุดเริ่มคัดออกไปรอบ 2
**ตกลงกับผู้ใช้**: รอบ 1 ไม่คัดออก (ยังคงใช้โจทย์ fib เดิม), เริ่มคัดออกจริงที่รอบ 2 (คัด 2, ใช้โจทย์ anagram เดิม), รอบ 3 คัด 1 (ใช้โจทย์ two_sum เดิม), เพิ่มรอบ 4 ใหม่ตัดสินผู้ชนะ (คัด 1 คนสุดท้าย) — รูปแบบคัดออก 5→3→2→1 เดิมยังคงอยู่ครบ แค่เลื่อนไปเริ่มช้ากว่าเดิม 1 รอบ
**โจทย์รอบที่ 4**: ตกลงกับผู้ใช้ให้ดึงจากคลังโจทย์จริงในฐานข้อมูล (`arcade_tasks` ระดับ hard ที่มีอยู่แล้ว 5 ข้อ, เดิมเป็น dead code ไม่เคยถูกใช้จริง) แทนการ hardcode โจทย์ใหม่
**แก้ไข**:
- เพิ่ม `PHASES.SHOP_3`, `PHASES.ROUND_4` และ `ROUND_TIMES` ที่เกี่ยวข้อง
- เขียนใหม่ `handlePhaseTransition()` ทั้งหมด: `ROUND_1→SUMMARY_1→SHOP_1→ROUND_2(คัด2)→SUMMARY_2→SHOP_2→ROUND_3(คัด1)→SUMMARY_3→SHOP_3→ROUND_4(คัด1สุดท้าย)→RESULT`
- แทนที่ `getTaskForRound` (dead code เดิม) ด้วย `getRound4Task()` — ดึงโจทย์ hard ตัวแรกจากคลัง DB (`dbTasks.hard[0]`) พร้อม fallback แบบ hardcode ที่เนื้อหาตรงกับโจทย์ DB ตัวแรกเป๊ะ (กรณี fetch ยังไม่เสร็จ/ล้มเหลว) ดึง `functionName` จากบรรทัด `def ชื่อฟังก์ชัน(...)` ในโค้ดตั้งต้นด้วย regex เพราะทั้งข้อมูล DB และ fallback ไม่มีคอลัมน์เก็บชื่อฟังก์ชันแยกไว้
- `evaluateRound(roundNum, eliminationCount)` เพิ่ม parameter ใหม่ และแยกกรณีรอบ 4 ให้ดึง `functionName`/`cases` จาก `getRound4Task()` แทน `TASK_TEST_CASES` แบบ static
- `BattleRoyaleGameplayView.jsx` เปลี่ยนจากคำนวณชื่อ/คำอธิบายโจทย์ภายในตัวเอง (ผ่าน translation key ตายตัว 3 รอบ) เป็นรับ `challengeTitle`/`challengeDesc` เป็น prop จาก parent แทน เพราะโจทย์รอบ 4 มาจาก DB (มีคอลัมน์ไทย/อังกฤษอยู่แล้ว) ไม่ใช่ translation key
- `botAI.js`: แก้ gate การซื้อ/ใช้ไอเทมของบอทให้แม่นยำขึ้น — เดิมเช็คแค่ `phase !== 'ROUND_1'` ซึ่งจะทำให้บอทพยายามใช้ไอเทมระหว่างหน้าสรุปผล (SUMMARY_*) ด้วยโดยไม่ตั้งใจ เปลี่ยนเป็นเช็คเฉพาะ `phase.startsWith('ROUND_') && phase !== 'ROUND_1'` สำหรับการใช้ไอเทม ส่วนการซื้อเพิ่ม `SHOP_3` เข้าเงื่อนไขเดิม
