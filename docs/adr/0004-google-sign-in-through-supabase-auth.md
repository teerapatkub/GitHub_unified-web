# Google sign-in ผ่าน Supabase Auth

ทั้งสองวิธีเข้าสู่ระบบ คืออีเมลกับ Google ใช้ Supabase Auth ทางเดียว ADR 0003 ย้ายอีเมลไปแล้ว แต่คง Google ไว้เป็นระบบของ server เอง
คือ server ตรวจ ID token ของ Google เองแล้วออก cookie session ของตัวเอง ตอนนี้ Google เปลี่ยนมาใช้ Google provider ของ Supabase แทน
ผู้ใช้ทั้งสองแบบจึงนับรวมในโควตา MAU เดียวกันของแผนฟรี และ server มีเส้นทางยืนยันตัวตนเหลือทางเดียว คือ bearer token ของ Supabase

บัญชี Auth ของ Supabase ที่ยังไม่ผูกกับบัญชีผู้เล่นใช้ API ไม่ได้ จะผูกได้ผ่าน endpoint เดียวเท่านั้น ซึ่ง browser เรียกครั้งเดียวหลังกลับจาก Google:
- ถ้ามีผู้เล่นหนึ่งคนที่อีเมลตรงกัน ให้ผูกกับผู้เล่นคนนั้น
- ถ้าไม่มีเลย ให้สร้างผู้เล่นใหม่ที่เลเวล 0
- ถ้ามีมากกว่าหนึ่งคน หรือผู้เล่นคนนั้นผูกกับบัญชี Auth อื่นไปแล้ว ให้ปฏิเสธ

ADR 0003 ไม่ยอมรับอีเมลที่ client ส่งมาเป็นหลักฐานความเป็นเจ้าของบัญชี แต่อีเมลที่ Google ยืนยันแล้วและ server อ่านจาก Supabase เองถือเป็นหลักฐานได้
ซึ่งตรงกับกฎของ flow Google เดิม การผูกจึงรับเฉพาะบัญชี Auth ที่มี Google identity ผู้ใช้อีเมลกับรหัสผ่านจะถูกผูกด้วยอีเมลที่ตรงกันไม่ได้

ทางเลือกที่ไม่เลือก:
- **คง Google แบบเดิม:** ไม่มีเพดานผู้ใช้และไม่ต้องแก้โค้ด แต่ต้องดูแลระบบ session สองแบบคู่กันตลอด
- **ผูกอัตโนมัติใน middleware ทุกคำขอ:** ทำให้คำขอใดก็ได้สร้างบัญชีผู้เล่นได้

ผลที่ตามมา:
- เจ้าของ OAuth client ต้องใส่ callback ของ Supabase ใน Google Cloud Console
- client secret ของ Google อยู่เฉพาะใน management env เท่านั้น
- ตาราง `player_google_sessions` ยังไม่ถูกลบ จะลบภายหลังด้วย migration ใหม่
