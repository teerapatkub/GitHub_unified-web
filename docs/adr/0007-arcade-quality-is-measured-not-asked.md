# คะแนนคุณภาพโค้ดของ Arcade มาจากการวัด ไม่ใช่จากโมเดล

## บริบท

ADR 0006 ให้ Gemini ให้คะแนนคุณภาพโค้ดทุกคำตอบ (เวลา ประสิทธิภาพ มาตรฐาน) ในวันเดียวกันนั้นผู้ใช้ตั้งคำถามว่า
เกมที่เน้นความเร็วแบบนี้ ผู้เล่นต้องรอ AI ตรวจหรือไม่ และเกณฑ์ที่แม่นและแน่นอนจะดีกว่าหรือไม่

สิ่งที่วัดได้:

- **Gemini ช้า:** free tier ใช้เวลา 13–14 วินาทีแม้ตอบประโยคเดียว (วัดเมื่อ 2026-10-20)
  - ถ้าผู้เล่นส่งวินาทีสุดท้าย finalizer ต้องรอผลภายใต้ room lock ทุกคนในห้องจึงรอหน้าสรุปนานขึ้น
- **โควตาฟรีหมดง่าย:** 5 คน × 4 รอบ บวกคลังคำตอบบอท
  - พอโควตาหมด ระบบถอยไปใช้คะแนนสำรอง ในรอบเดียวกันจึงมีคนได้คะแนนจาก AI และคนได้คะแนนสำรอง ซึ่งไม่เป็นธรรมที่สุด
- **คะแนนไม่แน่นอนและอธิบายไม่ได้:** ใช้ temperature 0 ก็จริง แต่โค้ดที่ต่างกันนิดเดียวอาจได้คะแนนต่างกันมาก
  - ผู้ให้บริการเปลี่ยนรุ่นโมเดลเมื่อไร คะแนนก็เปลี่ยน
  - บอกผู้เล่นไม่ได้ว่าเสียคะแนนตรงไหน
- **ยังมีช่องหลอกด้วยข้อความในโค้ด** และ free tier ส่งโค้ดผู้เล่นไปให้ Google

## สิ่งที่ตัดสินใจ

**การให้คะแนนใช้การวัดในเครื่องทั้งหมด** (`server/arcade/quality-probe.py` + `code-metrics.js`)

- probe รันคำตอบกับเทสของรอบหนึ่งครั้ง และอ่านโค้ด
- เทียบกับเฉลยที่วัดด้วยวิธีเดียวกัน ได้ 3 เกณฑ์ ข้อละ 0–100:

| เกณฑ์ | วัดอย่างไร |
|---|---|
| เวลา | จำนวนบรรทัดของผู้เล่นที่รันจริงทุกเทส (`sys.settrace`) เทียบกับเฉลย ไม่ขึ้นกับความเร็วเครื่อง ≤ 1.25 เท่าได้ 100 แล้วหัก 40 ต่อทุกครั้งที่เพิ่มเป็นสองเท่า วนไม่รู้จบได้ 0 มี error กลางทางได้ไม่เกิน 50 |
| ประสิทธิภาพ | ลูปซ้อนลึกกว่าเฉลย −30 ต่อชั้น · เรียก `sorted` `.sort` `.count` `.index` `.remove` `.insert` ในลูปเกินที่เฉลยใช้ −10 ต่อครั้ง (สูงสุด −40) · ยาวเกิน 2.5 เท่าของเฉลย −10 |
| มาตรฐาน | PEP 8 แบบเบา เฉพาะบรรทัดที่ผู้เล่นเขียนเอง: บรรทัดเกิน 79, เยื้องผิด, ช่องว่างท้ายบรรทัด, ไม่เว้นวรรครอบตัวดำเนินการ, ชื่อไม่เป็น snake_case, ตัวแปรที่ไม่ได้ใช้, `== None/True`, `except:` เปล่า, `;` · −8 ต่อข้อ (นับไม่เกิน 3 ข้อต่อกฎ) |

- คุณภาพ = ค่าเฉลี่ยของ 3 เกณฑ์ แล้วใช้สูตรเดิมจาก ADR 0006
  - โค้ดตั้งต้นที่ไม่ได้แก้ได้ 0
  - คุณภาพ × (0.5 + 0.5 × สัดส่วนเทสที่ผ่าน)
- ทุกข้อที่หักเก็บไว้พร้อมเลขบรรทัดใน `quality_rubric.findings` และแสดงในหน้าประวัติรอบ
- บอทใช้การวัดเดียวกันกับคลังคำตอบ ไม่ใช้โควตา
- การวัดเริ่มตั้งแต่ตอนกดส่ง (`submission-api.js`) และ cache ตามโค้ด
  - finalizer รอได้ไม่เกิน 6 วินาที เป็นแค่ตาข่ายกันกรณี Python ค้าง
- **ความเร็วในการส่ง** ยังเป็น `timeScore` ของ server เหมือนเดิม

**Gemini เหลือหน้าที่เดียว คือเขียนคำแนะนำหลังจบแมตช์** (`advise()` ผ่าน `POST /api/arcade/history/:historyId/advice` ใช้ id ของแถวประวัติแทน matchId+round ตามแผน เพราะหน้าประวัติมี id นี้อยู่แล้ว)

- ผู้เล่นเปิดดูรอบในหน้าประวัติแล้วคำแนะนำจึงโหลดตามมา
- ไม่มีผลต่อคะแนน
- เรียก Gemini ครั้งเดียวต่อรอบ แล้วเก็บใน `quality_feedback`
- ดูได้เฉพาะเจ้าของรอบ และหลังแมตช์จบแล้วเท่านั้น
- ถ้าไม่มีคีย์ โควตาหมด หรือเกิด error จะแสดงข้อความจากผลวัดแทน และไม่บันทึก

## ทางเลือกที่ไม่เลือก

- **คง Gemini ให้คะแนนไว้ (ADR 0006):** ช้า โควตาจำกัด และให้คะแนนต่างมาตรฐานกันในรอบเดียวกัน ตามเหตุผลข้างบน
- **วัดเวลาจริงด้วยนาฬิกา (`runtimeMs`):** เทสเคสเล็กมาก ค่าที่ได้จึงเป็นสัญญาณรบกวนจากโหลดของเครื่อง
  - ยังเก็บ `runtimeMs` ไว้ใน grader แต่ไม่ได้ใช้ให้คะแนน
- **สร้าง input ขนาดใหญ่ต่อโจทย์เพื่อวัด Big-O:** แม่นกว่า แต่ต้องเขียนตัวสร้าง input ให้ทั้ง 40 ข้อ จึงยังไม่ทำ

## กันการโกงตัววัด (เพิ่ม 2026-10-20 หลัง code review)

โค้ดผู้เล่นรันใน process เดียวกับ probe การตรวจครั้งแรกพบว่าโกงได้: เรียก `sys.settrace(None)` หรือแก้ `__main__.steps`
แล้วคำตอบที่ช้าจะได้คะแนนเวลาเต็ม (คุณภาพขึ้นจาก 57 เป็น 90 ในโจทย์ FizzBuzz) ตอนนี้ป้องกันไว้ 3 ชั้น:

- **ตรวจก่อนรัน:** ถ้าโค้ดอ้างถึงกลไกของตัววัด (`settrace`, `__main__`, `_getframe`, `gc`, `inspect`, `builtins`,
  `__closure__`, `_exit`, `sys.modules` ฯลฯ) จะไม่รันโค้ดนั้น และได้คุณภาพ 0 พร้อมเหตุผล
- **ตรวจระหว่างรัน:** หลังรันแต่ละเทส ถ้า tracer ถูกปิดไป (เช่นใช้ `getattr(sys, 'set' + 'trace')`) ก็ได้ 0 เหมือนกัน
- **ไม่มีอะไรให้แตะ:** ตัวนับขั้นและ marker ของผลลัพธ์อยู่ใน closure และผลเขียนตรงลง file descriptor 1
  การ print บรรทัดผลปลอมจึงไม่มีผล

นี่ไม่ใช่ sandbox ที่ปลอดภัยสมบูรณ์ คนที่ตั้งใจหาช่องใน Python มากพอยังอาจเลี่ยงได้
แต่กันวิธีที่ตรงไปตรงมาทั้งหมดที่พบแล้ว ถ้าเจอวิธีใหม่ ให้เพิ่มเทสใน `tests/arcade-code-metrics.test.js`

ตัววัดถือว่า "วัดไม่ได้" ใน 2 กรณี:
- **เฉลยวัดไม่ได้** (Python ไม่มีหรือค้าง): ใช้คะแนนแบบง่าย (`fallback`) และไม่ cache ทั้งคำตอบและเฉลย
- **เฉลยวัดได้แต่คำตอบค้างจนหมดเวลา:** ถือเป็นความผิดของคำตอบ ได้ 0

## ข้อจำกัดที่รู้อยู่

- `sys.settrace` นับเฉพาะบรรทัด Python งานภายใน built-in (เช่น `list.index` ที่วนทั้ง list) จึงไม่ถูกนับเป็นเวลา
  - ส่วนนี้ใช้เกณฑ์ประสิทธิภาพจับแทน (เรียกซ้ำในลูป)
- กฎ PEP 8 ตรวจแค่บางส่วน ไม่ได้ใช้ pycodestyle ทั้งชุด เพราะ server ไม่มี package นั้น

## ผลที่ตามมา

- calibration (`node scripts/arcade-tests/quality-calibration.js`):
  - เฉลยทั้ง 40 ข้อได้ 95+ ทุกเกณฑ์
  - คำตอบผิดในคลังบอท 81 แบบได้คุณภาพเฉลี่ย 94.0 (ความผิดถูกตัดสินด้วยเทส ไม่ใช่คุณภาพ)
- สมดุลบอท (`npm run sim:bots`): ปรับ `passMin` ของ easy/default/medium/hard เป็น 0.05/0.2/0.3/0.45 และ easy `passSpread` เป็น 0.38
  - คะแนนเฉลี่ยต่อรอบอยู่ใน ±2% ของค่าก่อน ADR 0005 ทุกระดับ
- ถ้าแก้กฎการวัด ต้องรัน calibration และ sim ใหม่ทุกครั้ง
